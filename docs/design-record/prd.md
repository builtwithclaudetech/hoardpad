## 1. Definitions

Terms used throughout, defined before use.

- **Document / doc** — a single text buffer shown in one tab. May be a file on disk or an unsaved scratch buffer.
- **Buffer** — the in-memory editable content of a document, which may differ from the on-disk file (dirty state).
- **Open folder** — a directory the user has explicitly opened as the working root (via "Open Folder"). Shown as a file tree. There is at most one active open folder per window in v1.
- **Open-folder root** — the resolved absolute path of the active open folder. This is the AI write sandbox boundary (see §6 AI panel, FR-26). Its user-facing label is **"document folder"** (FS-3, Decision B — FINAL, 2026-07-10): UI surfaces show `Document folder: <root>`, never the word "Sandbox" — the boundary itself is unchanged, only its display wording.
- **AI panel** — a floating, hotkey-toggled chat surface that reads doc/folder context and can act on files.
- **AI backend / provider** — one of three interchangeable implementations behind a single internal provider abstraction: Claude Code headless (`claude -p`), Anthropic API direct, or local LLM (Ollama/LiteLLM).
- **AI agency mode** — one of three settings governing how AI file operations are applied: `auto-apply` (default), `approve-each`, `read-only`.
- **Activity log** — an append-only record of every AI file operation, viewable in the UI.
- **`.hoard` file** — HoardPad's proprietary checklist document type (JSON on disk).
- **Session** — the set of open tabs, their buffer contents, cursor positions, and active tab, persisted so the app can restore them on next launch. The open folder is **not** part of the persisted session (FS-1, §9.2, Decision A — FINAL, 2026-07-10): it is recomputed every launch from a passed-in file, the first restored tab with a saved path, or My Documents.
- **TextMate grammar** — the same syntax-grammar format VS Code uses, consumed by AvaloniaEdit's TextMate integration for highlighting.
- **PCRE** — Perl Compatible Regular Expressions, the regex flavor for find/replace.
- **RID** — .NET Runtime Identifier (`win-x64`, `linux-x64`) for self-contained publish targets.
- **Reference hardware** — the reference machine for performance targets: a modern multi-core x64 workstation-class machine on a local SSD. Performance criteria are measured here.

## 2. Problem statement & motivation

The maintainer keeps a running "hoard" of notes, code snippets, drafts, and checklists open across two machines (Windows 10+ and Linux) and lives in a text editor all day. No existing tool covers all three needs at once:

- **Notepad++** is fast and tabbed but Windows-only, renders no Markdown, has no AI, and has no managed checklist type.
- **VS Code** has excellent Markdown and AI, but is heavy, project/IDE-centric, and its AI is extension-gated — it is not a fast "open a scratch file" notepad.
- **Obsidian** has strong Markdown and notes but is vault-centric, is not a general code editor, and its checklists are plain Markdown task lists rather than a managed, reorderable type.

**HoardPad v1 is an AI-first notepad** — a Notepad++-class editor, a built-in agentic AI host, and a first-class `.hoard` checklist type, delivered together as one native cross-platform binary. The wedge: Notepad++-class lightness and startup; a Markdown rendered-preview toggle (colorized source plus a one-button native-Avalonia preview — see FR-16 for the concrete feature set; "VS Code-grade" is the aspiration, not an acceptance promise); a built-in agentic AI panel that defaults to *acting* on the open folder rather than only chatting; and a first-class `.hoard` checklist document type.

**Deliberate priority — AI host in, autocomplete out.** v1 ships the full agentic AI file-write host but defers word/function autocomplete (§13) to v2. This is an intentional choice, not an omission: the agentic AI host is HoardPad's differentiating wedge over Notepad++ (which has neither), whereas autocomplete is a known AvaloniaEdit gap that is additive, not differentiating, and can arrive in a fast-follow without reworking the editor core. The solo-build schedule risk this priority carries is acknowledged in §10 (A-8) and §11.

## 3. Target users & usage context

**Primary user (v1): the maintainer.** A developer/creator running both Windows 10+ and Linux who works in a text editor continuously. Usage context:

- Opens scratch files and code files fast, often many at once across tabs.
- Edits Markdown frequently and wants a clean rendered preview without leaving the editor.
- Wants an AI copilot that can read the open documents and folder and directly create/edit/move/debug files, with a hard safety boundary and full undo.
- Maintains running checklists that must survive crashes and reorders.
- Runs the same workflow on two machines and expects parity.

**Secondary users:** none in v1. The product is built personal-first. Public-release machinery (store, telemetry, marketing, auto-update, signed installers) is explicitly deferred (§4, §12). The architecture should not preclude later multi-user use, but no v1 requirement assumes users beyond the maintainer.

## 4. Goals / non-goals

### 4.1 Goals

- Ship a single native cross-platform (win-x64, linux-x64) editor with Notepad++-class startup and editing responsiveness.
- Deliver tabbed multi-document editing with session restore and auto-save that never loses work.
- Provide TextMate-grammar syntax highlighting and code folding for the 20 specified languages.
- Provide Markdown colorized source and a one-button toggle to a rendered, read-only preview meeting the concrete FR-16 feature set (CommonMark + the named GFM extensions). ("VS Code-grade" is aspirational framing only; the acceptance basis is FR-16, not parity with VS Code.)
- Provide PCRE find/replace across three scopes: current file, all open files, in-folder.
- Provide a floating, hotkey-toggled agentic AI panel with three user-selectable backends, doc/folder context, and the ability to create/copy/move/edit/debug files.
- Make AI file operations safe by construction: sandboxed to the open-folder root, fully undoable, and logged.
- Provide a first-class `.hoard` checklist type with drag-reorder, durable auto-save, and three checked-item display modes.
- Ship dark (default) and light themes derived from the HoardPad brand palette's jewel-tone direction.

### 4.2 Non-goals (permanent for v1; reasons inline)

- **No telemetry / analytics.** Personal-first; privacy is a hard constraint. No usage data leaves the machine.
- **No network calls except the configured AI backend.** No update checks, no crash reporting, no remote config.
- **No public-release machinery** (store listings, marketing site, auto-update, signed installers). Personal use does not need it.
- **No real-time collaboration.** Single-user product.
- **No cloud sync.** Files live on local disk; the user syncs machines by their own means.
- **No WYSIWYG Markdown editing.** Rendered preview is read-only; edits happen in source view (FR-15).
- **No browser-runtime / web-stack editor** (Electron, Tauri, Monaco). Rejected in Phase 1; the product is native Avalonia.

### 4.3 Deferred (out of scope for v1, may arrive in v2+; see §12)

Multi-view split + synchronized scrolling; column/block editing; macro record/replay; plugin/extension system; function list; document map. These are deferred, not permanent non-goals.

For each payload the gate asserts **(1) the hook's decision** (`allow`/`deny`) **and (2) the resulting on-disk state, the activity-log entry (§9.3), and the undo-journal entry (§9.4)** — i.e. that the Archetype-A enforcement (the product's central bet) is the thing being deterministically gated, not a structurally-stronger path the PRD does not treat as acceptance-critical. Assertions (a)–(d) are evaluated here, deterministically. **The (i) gate asserts the classifier ROUTES the op, not that a cap FIRED (R4-mi6).** Each (i) payload is op #1 of its turn — under the cap — so the correct hook decision for an in-sandbox create/edit/overwrite is **`allow`**, and the gate asserts (1) that the classifier **routed** the op to the right bucket via the `stat` create-vs-overwrite split + the FR-38 magnitude predicate (create→FR-11, overwrite→FR-38, both→FR-40), and (2) that an under-cap op correctly returns `allow`. **Cap *firing* (the `deny`-past-cap behavior) is NOT assertable here** — it lives in the >cap poisoned-README fixture and the FR-38 / FR-11 / FR-40 Done-whens; a test author must not read (i) in isolation and expect `deny`, nor try to assert a cap at op #1. **The hook decision and the op-application are TWO harness steps, not one (R4-mi7).** A PreToolUse hook only returns `allow`/`deny` — for Archetype A the *agent* performs the write, so with no live agent in the deterministic gate the **harness itself applies the allowed `tool_input` through HoardPad's shared file-ops service** (the FR-39-replay mechanism, the Archetype-B execution path) so that the on-disk-state / activity-log / undo-journal assertions in (2) have an executor. The gate is therefore: step 1 = drive the production hook, capture its decision; step 2 = for an `allow`ed op, apply the `tool_input` via the shared service, then assert on-disk + log + journal. **The deterministic gate now also includes a cross-continuation no-re-arm step (R5-BL1):** after a >cap trip, a **second** crafted-payload batch is driven into the **same conversation-keyed cap-state instance** (simulating the HoardPad-initiated continuation turn — a fresh invocation / `session_id` resuming the same conversation-keyed set) and the gate asserts the **(N+1)th cumulative distinct file still confirms** (the set did **not** reset across the continuation) — the deterministic executor for FR-40's cap-state-lifetime property, defined in SPIKE-3 (§11.1) and folded with the substitution-after-pause assertion (R5-mi3). This proves no-re-arm without a live LLM. *(Hardlink note, R3-MA4/Lane 3: over-counting a hardlinked file in the writable-set predicate is a **safe-direction inaccuracy** — it over-counts, so FR-10(a) downgrades **earlier**, never later; acceptable.)* **Owner:** `unit-test-engineer`; depends on the production hook script (FR-24), the shared-file-ops replay mechanism (FR-39), and the SC-5 fixture set (A-6). *(Pending SPIKE-3 — the hook script and its `tool_input` schema are confirmed in the Phase-4 `claude -p` contract spike, §11.1.)*

### 6.1 Editing core & tabs

**FR-1 — Tabbed multi-document editing.** The app shows open documents as tabs in a single window; the user can switch, reorder (drag), and close tabs.
*Done when:* opening N files yields N tabs; clicking/keyboard-switching changes the active buffer; dragging a tab changes its order; closing a tab removes it and focuses an adjacent tab.
*Build note:* tab drag-reorder requires a custom reorder behavior — Avalonia's `TabControl` does not provide it out of the box (tech-design to specify).

**FR-2 — New scratch buffer.** The user can create a new untitled buffer not backed by any file.
*Done when:* a "New" command opens an empty editable tab labeled untitled and marked unsaved; it persists across session restore (FR-19) without a file path.

**FR-3 — Open file.** The user can open an existing file via dialog, command-line argument, or "Open With" OS association.
*Done when:* the file's contents appear in a new tab; passing a path as a CLI arg on launch opens it; the tab title is the file name.

**FR-4 — Save / Save As.** The user can save the active buffer to its file, or to a new path via Save As.
*Done when:* Save writes the buffer to disk and clears the dirty marker; Save As prompts for a path, writes there, and rebinds the tab to the new path; saving a scratch buffer routes through Save As.

**FR-5 — Dirty-state indicator.** Each tab visibly indicates unsaved changes.
*Done when:* editing a saved buffer shows a dirty marker on its tab; saving clears it; closing a dirty tab prompts to save/discard/cancel.

**FR-6 — Standard editing operations.** The editor supports caret navigation, selection, cut/copy/paste, undo/redo, line operations (duplicate, delete line, move line up/down), and configurable line endings and encoding display.
*Done when:* each operation works via keyboard shortcut and (where applicable) menu; undo/redo traverses the edit history; the active buffer's encoding and line-ending style are shown in the status bar.
*Build note:* move-line / duplicate-line are custom `TextDocument` commands (not built into AvaloniaEdit); encoding detection on open needs a small detection lib (BOM sniffing + a charset detector such as `UTF.Unknown`). Tech-design to specify.

### 6.2 Syntax highlighting & folding

**FR-7 — TextMate highlighting for 20 languages.** Syntax highlighting via AvaloniaEdit TextMate grammars for: Markdown, HTML, JavaScript, CSS, Python, C#, XML, JSON, SQL, Rust, TypeScript, YAML, TOML, Shell/Bash, PowerShell, Dockerfile, C, C++, Java, Go.
*Done when:* SC-3 passes for all 20; language is auto-detected by file extension, with a manual language-override selector in the UI.
*Build note:* `TextMateSharp.Grammars` covers roughly 18 of the 20 out of the box; **TOML is likely absent and Rust may lag**, so supplemental `.tmLanguage.json` grammars are bundled as app embedded resources and surfaced through a custom `IRegistryOptions`. **FR-8 — Language auto-detection + manual override.** Language is chosen by file extension; the user can override the language for the active document.
*Done when:* a `.py` file highlights as Python without intervention; selecting a different language from the override control re-highlights immediately; a scratch buffer defaults to plain text until a language is chosen or it is saved with a recognized extension.

**FR-9 — Code folding.** Foldable regions (by brace/bracket and indentation heuristics per language family) can be collapsed and expanded. TextMate grammars provide tokenization only — **not** folding regions — so folding is delivered by a small set of reusable strategies rather than the grammar: (1) brace/bracket folding (C-family, JS/TS, Java, Go, Rust, C#, CSS, JSON); (2) `XmlFoldingStrategy` (XML, HTML); (3) indentation folding (Python, YAML, Markdown).
*Done when:* fold indicators appear in the gutter for foldable regions; clicking collapses/expands; folded state does not corrupt buffer content; fold state need not persist across session restore in v1.

### 6.5 Session restore & auto-save

**FR-19 — Session restore (with restore-time conflict detection for changed-on-disk files, B7).** On launch, the app restores the prior session: all open tabs (including unsaved scratch buffers and unsaved edits to on-disk files), the active tab, per-tab cursor position, and the open folder. **Stale-buffer-vs-changed-disk conflict (B7 — prevents silent loss on next Save):** recovery snapshots for `kind: file` tabs **record the on-disk file's content hash + mtime at snapshot time** (mirroring FR-28(ii)'s machinery). On restore, if the current on-disk file **diverges** from the snapshot's recorded hash (the file changed under a dead app — the other synced machine, a sync daemon, any tool), HoardPad surfaces a **conflict** (keep recovered buffer / keep disk / show diff) instead of silently restoring the stale buffer and arming a clobbering Save. This is the same divergence-detection FR-28(ii) requires for AI undo; the restore path is equally able to clobber and must not be exempt.
*Done when:* SC-7 passes; an unsaved scratch buffer's content reappears; a dirty on-disk file whose disk content is **unchanged** reopens with its unsaved edits and dirty marker intact; a dirty on-disk file whose disk content **changed while the app was dead** surfaces a keep-recovered / keep-disk / diff conflict on restore rather than silently restoring and arming a clobbering Save (restore-with-externally-changed-disk test).

**FR-20 — Auto-save / crash protection for text buffers.** Buffer contents (including unsaved scratch buffers and unsaved edits) are periodically persisted to a recovery store so an ungraceful termination loses at most the configured interval of work.
*Done when:* killing the process mid-edit and relaunching restores buffer content to within the last auto-save interval; the auto-save interval is configurable (default **5 seconds** of idle after a change, debounced; hard ceiling **30 seconds** since last persist). Auto-save to the recovery store does **not** silently overwrite the user's on-disk file — explicit Save (FR-4) is the only path that writes the user's file.

**FR-21 — Backup retention.** The recovery store keeps the latest recoverable state per buffer; on successful explicit save and clean close, recovery data for that buffer is cleared.
*Done when:* after a clean save+close, no stale recovery artifact remains for that buffer; after a crash, exactly one recoverable state per previously-open buffer is available.

### 6.6 AI panel

**Provider model — two archetypes behind one selector (architectural premise for §6.6).** The AI abstraction is **not** a single flat provider interface. The three user-selectable backends fall into two archetypes, and the difference is load-bearing for how file ops are captured and made safe:

- **Archetype A — delegated-agent backend (`claude -p`, the default).** The Claude Code agent runs *its own* tool-use loop and performs file operations itself. HoardPad supplies context and the sandbox boundary, launches the agent process, and **intercepts/observes the agent's file-tool calls** (via tool-permission hooks). HoardPad does not author the agent loop here — it gates it.
- **Archetype B — driven-completion backend (Anthropic API direct, local LLM via Ollama/LiteLLM).** HoardPad *owns* the agent loop: it defines the file-op tools, parses the model's tool-call requests, and executes each operation itself.

Both archetypes route every file operation through **one shared HoardPad file-ops service** — that single service (sandbox check + undo journal + activity log) is what delivers **uniform logging + undo-journal structure; enforcement strength differs by archetype** (per-op-atomic and TOCTOU-free in the driven-completion archetype where HoardPad is the writer; observe-and-veto in the delegated-agent archetype — see C-8, FR-26). The shared service is **not** a "uniformity guarantee" for enforcement; it standardizes the log/journal shape, not the enforcement strength. Tech-design owns the exact interface split.

**FR-22 — Floating, hotkey-toggled panel.** The AI panel is a floating surface toggled show/hide by a configurable hotkey. For v1 the toggle hotkey is **app-scoped** (Avalonia `KeyBinding` / `KeyGesture`) — zero platform shim, Wayland-safe. A true **system-global** hotkey is deferred to v2 (no portable Wayland global-hotkey API exists; adding one would break SC-8 parity). The "floating" panel is implemented as an **in-window overlay** (Avalonia `Panel` / `AdornerLayer` layered over the editor), not a separate always-on-top OS window — this floats over the editor without reflowing layout while sidestepping Wayland windowing quirks.
*Done when:* a single app-scoped hotkey shows the panel if hidden and hides it if shown; the panel floats over the editor as an in-window overlay without permanently reflowing tab/editor layout; the hotkey is reconfigurable in settings; the panel works identically on Windows and on Linux under Wayland.

**FR-23 — Three selectable backends.** The user selects the active AI backend in settings from: (1) Claude Code headless (`claude -p`) — **default** (Archetype A), (2) Anthropic API direct, (3) local LLM via Ollama/LiteLLM (both Archetype B). All three sit behind the provider model above and share one file-ops service.
*Done when:* changing the backend in settings routes the next AI request through that provider with no other behavioral change to context or agency; the default on first run is Claude Code headless; switching providers does not require restart. For `claude -p` (Archetype A), file ops are performed by the agent itself and captured by HoardPad via tool-permission hooks; for the API/local backends (Archetype B), HoardPad performs the file ops directly; in **both** cases the sandbox (FR-26), undo journal (FR-28), and activity log (FR-29) are enforced by HoardPad's shared file-ops service.

**FR-24 — Backend configuration + readiness check.** Each backend exposes its required configuration (e.g. Anthropic API key; Ollama/LiteLLM endpoint + model name; for `claude -p`, the CLI path) and a readiness check. The `claude -p` readiness check must verify more than PATH/version — it must confirm the CLI is **installed AND authenticated** (per A-1), meets a minimum version, and (if hooks are used) has its hook config honored:
1. **Authenticated, not just present.** A real test call — e.g. `claude -p --output-format json "say ok"` — succeeds. A version/PATH probe alone is insufficient (an unauthenticated CLI passes PATH but fails at request time).
2. **Minimum version (M4 — Edit-deny must be verified at this version).** The installed `claude` meets a documented **minimum supported version** that provides the flags HoardPad depends on (`--output-format stream-json`, `--include-partial-messages`, `--json-schema`, the `--permission-mode` values, hooks, and `--max-budget-usd`) **and at which `Edit`-tool deny enforcement is verified**. (Edit-deny was once a closed-"not planned" CLI bug; the minimum version must be one where it is confirmed working, and the M3 self-test below is the runtime guard against regression.) *Minimum supported `claude` version: **2.1.179** — PINNED by SPIKE-3 (§E, live-verified 2026-06-19). **FR-25 — Context model.** The AI has read context on: the current document, all open documents, and the open-folder file tree. The available **read context is equivalent across backends**; the **delivery mechanism differs** by archetype — native file tools scoped to the same root for `claude -p` (Archetype A); inline context plus HoardPad-implemented read tools for the API/local backends (Archetype B). It is the *available context*, not the wire format, that is equivalent.

Context is assembled in tiers to stay within model and budget limits rather than dumping everything:
- **(a) Always inline:** the active document (full, or a window around the cursor if very large); a **structural listing** of all open tabs (path, language, dirty flag, size — **not** full contents); and the open-folder tree as **paths only** (names + sizes, depth- and entry-capped, respecting `.gitignore`).
- **(b) On demand:** the contents of non-active documents and of other folder files are fetched via a **Read tool** when the model asks for them — native Read for `claude -p`, a HoardPad-implemented Read tool for API/local.
- **(c) Bounded:** every request is capped by a per-request **token budget**; oversize files are truncated with explicit truncation markers. For `claude -p`, lean on **prompt caching** of the stable context block to keep cost/latency down.

*Done when:* an AI request can reference content from a non-active open tab and from a file in the open-folder tree it was not explicitly handed (resolved via the on-demand Read path); the always-inline tier never ships full non-active-doc contents or full folder file contents; a per-request token budget is enforced and oversize content is truncated with a marker; the equivalent context is reachable on all three backends.

**FR-26 — Sandboxed file agency (hard safety boundary).** The AI can create, copy, move, edit, and delete files, but every write/move/create/delete is constrained to the resolved open-folder root and its descendants. Writes that would escape the root (including via `..`, absolute paths, or symlinks resolving outside the root) are refused.

**Enforcement by archetype — NOT uniform; B is structurally stronger than A (M5/M6, honesty fix).** The two archetypes enforce the sandbox by **different mechanisms with different strength**:
- **Archetype B (API/local) — per-op atomic, TOCTOU-free.** HoardPad *executes* every op itself: it canonicalizes-then-writes in one step, captures the before-image as the writer, and there is no separate process racing the write. This is the structurally stronger path.
- **Archetype A (`claude -p`) — observe-and-veto.** The agent performs ops itself; HoardPad enforces the sandbox **two ways at once**: (1) intercepting the agent's file-tool calls via the deny-by-default PreToolUse hook and applying canonicalize-and-verify (deny anything not at-or-under the resolved root) *before* the op applies; and (2) the deny-by-default tool matcher (FR-24 contract) disabling `Bash` / `mcp__*` / `MultiEdit` / `NotebookEdit` / `Agent`, because path-based enforcement cannot police a shell write such as `bash -c 'echo > /etc/...'`. Because HoardPad observes-and-vetoes rather than executing, Archetype A carries a **residual TOCTOU window** (a path component could be swapped to a symlink between the hook's check and the agent's write, which a hook against a writer it does not execute cannot fully close), a before-image captured by a separate process racing the write, a dependency on the CLI's deny correctness, and a silent-disarm failure mode (closed by the M3 self-test). These are documented limitations, not bugs.

**Op vocabulary — rename canonicalizes to `move` (MA11).** HoardPad's internal file-op vocabulary is `create` / `copy` / `move` / `edit` / `delete` (§9.4). A **rename is canonicalized to `move`** (there is no distinct `rename` op), so a rename onto an existing file is a clobbering `move` that hits FR-10(b)(ii)'s clobber-confirm and FR-28's clobbered-destination capture — and a rename that would replace a file currently open in a dirty tab is reconciled (conflict-prompted), never silently orphaning the live dirty buffer. Tech-design must implement rename as `move` (not delete-dest-then-move, which would bypass the clobber confirm).

**Reachable file ops differ by archetype (R3-BL1) — the full vocabulary is Archetype-B-only.** The `create`/`copy`/`move`/`edit`/`delete` vocabulary above is the **internal** model; the ops an archetype can actually emit differ:
- **Archetype A (`claude -p`):** under the deny-by-default matcher (FR-24) the reachable file ops are exactly **create / full-overwrite / partial-edit**. `delete`, `move`, `copy`, `rename`, and shell-`truncate` are **foreclosed by the Bash deny** (live-confirmed: asked to delete/move/truncate, the agent reaches for `rm`/`mv`/`:>`, all denied by the matcher; `claude` has no native delete/move/copy/rename/truncate tool). A truncate-to-0 reaches Archetype A only as a `Write` of empty content onto an existing file (caught by the FR-38 overwrite predicate). So **FR-38's `delete`/`truncate` counting, FR-28's clobbering-move capture, FR-10(b)(ii)'s clobber confirm, and MA11's rename==move are Archetype-B-only protections** — they guard ops Archetype A cannot reach, and a `/code` agent must not build them as live branches in the Archetype-A hook. The **Archetype-A injection-defense fixture uses Write-overwrites plus a single-hunk full-file `Edit`** (not a delete), per FR-38's Done-when.
- **Archetype B (API/local):** the full `create`/`copy`/`move`/`edit`/`delete` vocabulary is reachable, because HoardPad defines the tools and executes the ops itself; the Archetype-B fixture exercises `delete`/clobbering-`move` directly through the shared file-ops service.

**Per-op interception liveness — POSITIVE invocation tracking, not a negative error signal (MA14; reframed R3-mi1).** Every hook-failure mode (timeout, malformed config, missing command) results in a **silent allow** with no stderr / result-field / negative CLI signal — so liveness **cannot be detected by listening for an error**, and the design must track it positively. HoardPad therefore confirms the hook **fired for each write** by **matching each `stream-json` tool-use event the agent emits against an observed per-op hook callback**: a tool-use event for a write tool with **no matching hook invocation** is the degrade signal (the hook armed at startup — proven by the M3 self-test — but is no longer being honored per op). If a hook invocation fails/times out mid-turn (see FR-24/MA1 timeout-fail-open) or an expected per-op hook callback is **absent** for an observed write tool-use event, the backend is treated as degraded mid-turn and FR-10(c)'s block/confirm-remaining-or-halt rule applies; ops already applied before detection are logged. (No CLI-emitted degrade signal exists; absence-of-expected-invocation is the only detection channel.)

**Stated honestly:** for `claude -p`, the sandbox / undo / log guarantees are **contingent on interception being active**. The shared file-ops service provides **uniform logging + undo-journal structure** across both archetypes, but **enforcement is not uniform** (per-op-atomic in B; observe-and-veto with the residual TOCTOU/version dependencies above in A) — see C-8. If hook interception proves infeasible in tech-design, the fallback is a **degraded mode** — session-granularity undo/log via a before/after **tree-snapshot diff** of the open-folder root — labeled and surfaced to the user as degraded (not silently substituted for per-op guarantees), and forcing `approve-each` (FR-10(c)).

*Done when:* SC-5(d) passes under full per-op interception (the SC-5 acceptance basis: interception "Met," degraded mode "Partial" with the degraded state surfaced in the UI); a scripted attempt to write to a path outside the resolved root (absolute path, `../` traversal, and a symlink pointing outside the root) is each refused and recorded as a blocked op in the activity log; **the hook script's `deny` branch is positively exercised in isolation (M6)** by piping crafted `tool_input` JSON (including a symlink-escaping-root case and a path-component-swap race case) and asserting the `deny` decision, since the live model may voluntarily refuse and never hit the canonicalize branch; for `claude -p`, the **allowlist principle is tested, not a fixed denylist (R4-MA2)**: `Read` / `Edit` / `Write` are confirmed allowed (subject to the sandbox check) and **every other tool is confirmed denied-by-default** — the assertion drives the `*`-matcher with a representative spread of non-allowed tools (`Bash`, `mcp__*`, `MultiEdit`, `NotebookEdit`, `Agent`, **plus a randomly-chosen non-allowlisted tool drawn from the *current* live `claude` roster** — not any fixed name, since the roster drifts with the CLI version, R5-mi1; e.g. whatever the installed version offers beyond `Read`/`Edit`/`Write`) and asserts `deny`, proving the **default** denies an unknown tool rather than relying on a hard-coded denylist; with **no open folder**, AI file-write agency is disabled entirely and the panel indicates write actions are unavailable (read/chat still allowed).

**FR-27 — Agency modes (with smart auto-downgrade).** Three agency modes selectable in settings: `auto-apply` (default — file ops apply immediately within the sandbox), `approve-each` (each file op requires explicit user confirmation before it applies), `read-only` (AI may read and chat but performs no file ops). **`auto-apply` is not unconditional:** per **FR-10**, an individual op under `auto-apply` is **automatically downgraded to a one-time `approve-each` confirm** when the root is home/large (FR-10(a)), the op is undo-unavailable or clobbering (FR-10(b)), or the backend is degraded (FR-10(c)); and per **FR-11** a turn that exceeds the per-turn create cap pauses for confirm. This reconciles the `auto-apply` default with the prompt-injection threat model (NFR-10) and the "every write undoable" constraint (C-4) — silent apply is reserved for in-bounds, reversible, non-clobbering ops on a scoped root.
*Done when:* in `auto-apply` on a small/non-home root, a reversible in-bounds op writes to disk without prompting (still sandboxed + logged + undoable); the FR-10 triggers each force a confirm before applying (verified per FR-10's Done-when); the FR-38 per-turn destructive-op cap, the FR-11 per-turn create cap, and the FR-40 per-turn distinct-files-touched cap each pause for a confirm when exceeded; in `approve-each`, every op shows a confirm/reject prompt and applies only on confirm (and an **unanswered** `approve-each` confirm fails closed → queues to the FR-39 pending-proposals surface, per FR-24/BL1); in `read-only`, the AI cannot create/move/edit/delete and any such attempt is refused with a clear message.

**FR-10 — Auto-apply smart auto-downgrade to approve-each (AI safety; relocated here from the §6.3 reserved band, mi12; Decision 1, resolves B4/B5/M9/M10).** When the active agency mode is `auto-apply` (FR-27), HoardPad **automatically downgrades the *individual operation* to a one-time `approve-each` confirm** (a blocking confirm/reject shown before the op applies) whenever **any** of these triggers holds — the user is not silently auto-applied through an irreversible, clobbering, or unscoped action:
- **(a) Large or home root (writable-set count, MA9; computable predicate + op-time re-count, R3-MA4/R3-MA1-MA10).** The resolved open-folder root (FR-26) is the user's home directory (`$HOME` / `%USERPROFILE%`) **or** the **writable set** under that root exceeds a configured file-count threshold. The writable set is the set the AI can actually mutate, so it must reflect real blast radius — **NOT** the `.gitignore`-filtered tracked-file view (MA9). **(Backstop role corrected, R4-BL2:** the large-root downgrade is **NOT** the backstop for the mass-*partial-edit* / sub-threshold-overwrite class FR-38 excludes — that role belongs to **FR-40** (the per-turn distinct-files-touched cap, which counts every overwrite regardless of magnitude). FR-10(a) bounds blast radius by *how many files exist* in the root; it does **not** bound *how many an injection mutates* — overwriting in place does not change the writable-descendant count, so FR-10(a) never fires for a sub-threshold mass overwrite on a medium root. The two controls are orthogonal.**)**
  - **"Writable set" defined as a bounded, early-exitable predicate (R3-MA4).** Count **regular-file descendants the process can open for write**, **resolving symlinks to their canonical paths and counting each canonical target once** (with a **cycle guard** so a symlink loop cannot cause an unbounded walk or hang); **do not cross mount boundaries** into a mounted tree under the root; **exclude special files** (devices, sockets, FIFOs). **Abort the walk at threshold+1** — only "over threshold?" is decided, the exact count is irrelevant — so the walk is bounded even on a root containing a 200k-file `node_modules`. **Run the walk off the UI thread** so folder-open never blocks (SC-1/SC-2 budgets are preserved). This replaces the unbounded "every descendant counts" recursive `stat` wording: there is **no `.gitignore` filtering** — the predicate counts all writable regular-file descendants per the rules above — but it is the early-exit predicate, not a full enumeration.
  - **Re-counted at op-time, not only at folder-open (R3-MA1/MA10).** Because this large-root downgrade bounds the *existing-file* blast radius (the orthogonal control to FR-40's mass-mutation backstop, R4-BL2), a folder that grows past the threshold mid-session (a sync daemon, multi-turn legitimate creates) must still trigger the downgrade. The threshold check is therefore **re-evaluated at op-time (or on a debounced file-watch of the root)**, not cached from folder-open — cheap given the abort-at-threshold+1 predicate above. The downgrade arms whenever the current writable-set count is over threshold, not only if it was over at open.
  *Default trigger: root == home dir, OR writable-set count > 2,000 files. The threshold and the home-dir rule are **tunable (FR-35)** and tech-design-confirmable (Phase 4).* When this trigger fires, it is announced once ("N files writable by the AI; auto-apply is downgraded to approve-each for this root"); the home-dir trigger records `downgradeReason: home-root` and the threshold trigger records `downgradeReason: large-root` (§9.3, R3-mi8).
  - **User-overridable, default ON (FS-5, Phase 8, docs/decisions.md DR-1).** FR-10(a) is no longer unconditional: Settings ▸ AI safety carries **"Confirm each AI edit in large/home folders"** (default **ON** = this trigger, as specified above). **OFF** disables ONLY this (a) trigger — auto-apply then applies silently on a home/large root too — while FR-10(b)/(c), the FR-11/FR-38/FR-40 per-turn caps, FR-26's boundary, and every undo/log guarantee are unaffected in either state (the toggle changes nothing but the confirm-vs-silent decision on an already in-bounds op). The Phase-8 build implements a scoped-down predicate (computed once per session-arm rather than re-counted at op-time; a best-effort bounded walk rather than the full mount-boundary/symlink-cycle-guard predicate) — see DR-1 for the exact gap vs. this spec.
- **(b) Undo-unavailable or clobbering op.** The op is **(i)** an overwrite, truncate, or delete of a file over the snapshot size cap (FR-28(iii)) — undo would be unavailable; the cap check uses the **pre-op** file size, never post-op (mi3), so a 9 MB→0-byte truncate is treated as an over-cap op — **or (ii)** a `move`/`copy` whose destination **already exists** (a clobbering op that destroys the destination; a **rename canonicalizes to `move`**, MA11, so a rename onto an existing file hits this branch). These confirm **even on a small/non-home root**. **Archetype scope (R3-BL1):** branch (ii) (clobbering move/copy/rename) is reachable **only in Archetype B** — `move`/`copy`/`rename` are Bash-foreclosed for Archetype A (FR-26). For Archetype A, branch (i)'s reachable cases are an over-cap **overwrite** (whole-file `Write`/full-file `Edit` onto an existing file) or an over-cap **truncate-to-0** (a `Write` of empty content onto an existing file); `delete` is Archetype-B-only. A clobbering **full-overwrite** (whole-file `Write` onto an existing file that is *under* the size cap) gets **no individual clobber confirm** under (ii) — it is governed only by the FR-38 destructive cap; this asymmetry vs a clobbering move (which always confirms) is stated in §9.3's counting rule (mi3).
- **(c) Degraded backend / mid-turn degrade (MA14).** The active backend is running in **degraded mode** (no per-op interception, FR-26). In degraded mode the whole session runs as `approve-each` (per-op confirm is the only safe granularity when interception is unavailable). **Per-op liveness + mid-turn degrade:** the interception hook must affirmatively confirm it armed **each** write (a per-op hook-liveness check, FR-26); if degrade is **detected mid-turn** (a hook invocation fails/times out — see FR-24/MA1's timeout-fail-open — or the startup-armed hook stops being honored), HoardPad **blocks/confirms the remaining ops or halts the turn**, and ops already applied before the degrade are logged. Ops are never silently auto-applied after a detected degrade.
*Done when:* with `auto-apply` selected and a home/large root open, an AI create/edit shows a confirm before applying; with a small non-home root, a normal in-bounds partial edit applies silently but an over-cap overwrite/truncate/delete and a clobbering move/copy/rename each show a confirm; exceeding the FR-38 destructive-op cap or the FR-11 create cap pauses for a confirm; in degraded mode every op shows a confirm; a fault-injection test that starts healthy and stalls the hook after op 2 of 5 asserts ops 3–5 are not silently auto-applied (MA14); a scripted fixture (poisoned README + benign prompt, B5) under each condition produces the specified confirm/silent outcome and is recorded for the sign-off file. The downgrade is recorded in the activity log with `agencyMode` reflecting the **effective** mode for the op and `downgradeReason` recording **why** it fired (§9.3, MA13), so the sign-off fixture can assert the safety net engaged for the right reason.

**FR-11 — Per-turn create-count cap (AI safety; relocated here from the §6.3 reserved band, mi12; Decision 1 / M10).** A single AI turn may create at most a configured number of new files before HoardPad pauses and requires a one-time confirm to continue — bounding a mass-create injection (NFR-10) under `auto-apply`. *Default cap: **25** new files per turn; tunable (FR-35); **MEASURED (SPIKE-3 §E, 2026-06-19)** — basis: 25 creates in one unconfirmed turn is a mass-create injection signal, covers a one-small-project-scaffold heuristic, 2.5× the FR-38 destructive cap since creates are lower-risk.* **A create is recognized via `Write` OR `Edit` (R4-BL1, live-reproduced):** the hook performs the `stat`/existence check on the target of **both `Write` and `Edit`** (not `Write.file_path` only) — a `Write` **or** an `Edit` whose target does **not** exist is a **create** counted toward this cap. In particular, **an `Edit` with empty `old_string` on a non-existent path is the agent's file-create idiom** (payload `{file_path, old_string:"", new_string, replace_all:false}`), and it counts toward FR-11 **and increments the FR-40 files-touched counter**. This closes the live-reproduced bypass where a `Write`-keyed cap left the agent free to create additional files through `Edit`; the matcher **cannot** deny `Edit` (it is the legitimate partial-edit path), so the cap logic itself must route `Edit`-on-a-nonexistent-path to this create cap. The `stat` runs inside the FR-26 residual-TOCTOU window already disclosed (and see R4-MA4 below for the stat-race misroute and why FR-40 is misroute-invariant). **Cap mechanics (MA12):** the cap **stays tripped after a confirm — the counter does NOT re-arm** (every further create of that class confirms; the counter is not reset), so an injection cannot chain N-at-a-time through confirm-fatigue. For Archetype A the hook-side counter must **accumulate across the agent's internal tool loop** within one HoardPad invocation (one `requestId`), not reset per internal tool call — verified against a real `claude -p` turn making >25 internal Writes (and >25 internal `Edit`-creates) in SPIKE-3 — and the **no-re-arm tripped state is further persisted by HoardPad across continuation turns**, keyed to the user-initiated conversation rather than the per-invocation `requestId` (the same conversation-scoped lifetime governs FR-11/FR-38/FR-40 — see FR-40's *Cap-state lifetime* clause, R5-BL1). **"Pause→confirm→resume" is not literal in `-p` (mi2):** a stateless single-shot `-p` turn cannot pause-then-resume; the hook **denies** past the cap, and "continue" is a **new** turn HoardPad initiates after the confirm (`--max-budget-usd` is a coarse cost ceiling, not a precise per-op budget). The same no-re-arm semantics apply to the FR-38 destructive-op cap by analogy.

**Cap integrity DEPENDS ON the deny-by-default matcher (R3-MA3) — the cap and the matcher are not independent safety layers.** The per-turn caps (FR-11 here and FR-38) are only as strong as the FR-24 deny-by-default matcher foreclosing **every non-counted filesystem-effecting path**. Live-confirmed: a `Write`-keyed counter that capped creates at N but left **Bash allowed** was defeated — on hitting the cap the agent escalated to `AskUserQuestion` (which auto-resolves in non-interactive `-p`) and created the remaining files via an allowed `Bash` redirection; re-run with the matcher denying Bash and every non-`Read`/`Edit`/`Write` tool, the cap held at exactly N. So a capped `-p` agent **will attempt tool substitution** (`Bash`, `AskUserQuestion`), and the matcher must deny **both** (and every other FS-effecting/spawn vector) or the cap is worthless. This dependency is verified in SPIKE-3.
*Done when:* a scripted turn attempting to create more than the cap is denied at the cap with a confirm-to-continue prompt; confirming lets HoardPad initiate a continuation turn; rejecting ends the turn with the already-created files intact and logged; the hook-side counter is verified to accumulate across an agent's internal tool loop and to stay tripped (no reset) after a confirm (SPIKE-3); **>cap creates routed through `Edit` (empty `old_string` on a non-existent path) are held at the FR-11 cap exactly as `Write`-creates are, and are counted by FR-40 (R4-BL1, SPIKE-3 / A-6 fixture)**; **a turn whose `Write` is capped does NOT achieve further creates via any other tool — verified by driving >cap creates with Bash allowed-but-counted vs Bash denied, confirming only the denied case holds the cap (R3-MA3, SPIKE-3).**

**FR-38 — Per-turn destructive-op cap (AI safety; NEW 2026-06-14 round 2; BL2, resolves round-1 B5 / MA8; classifier defined as a hook-evaluable predicate + archetype split, 2026-06-14 round 3, R3-BL1).** A single AI turn may perform at most a configured number of **destructive** file operations before HoardPad pauses and requires a one-time confirm to continue — the symmetric sibling of FR-11's create cap, closing the silent in-bounds mass-edit/delete gap that FR-11 (which caps only creates) left open. *Default cap: **10** destructive ops per turn; tunable (FR-35); **MEASURED (SPIKE-3 §E, 2026-06-19)** — basis: ~10 full-file overwrites in one batch flags injection vs a legitimate large refactor, ~1/2.5 of FR-11 (higher-risk ops warrant a lower cap).*

**Counted-op classifier — a hook-evaluable predicate over `(tool_name, target_pre_op_bytes, proposed_bytes)` (R3-BL1).** "Full-overwrite vs partial edit" was previously asserted but never defined against what the PreToolUse hook actually sees; the `claude` tool protocol (live-confirmed at 2.1.161) exposes only `Write` (`{file_path, content}`, whole-file) and `Edit` (`{old_string, new_string, replace_all}`, string-replace), neither of which maps to a destructive/non-destructive split on its own. The classifier is therefore defined as a predicate the hook evaluates per op:
- An op **counts toward the FR-38 destructive cap** if it is a **`delete`** (Archetype B only — see below), **OR** a write whose **target file already exists** (the hook does a `stat`/existence check on the `Write` **or** `Edit` target — see the create-vs-overwrite split below, extended to `Edit` per R4-BL1) **AND** whose proposed content is a **whole-file `Write`**, **OR** **shrinks or replaces ≥ X% of the prior bytes** (`X` is tunable (FR-35); **MEASURED X = 80% (SPIKE-3 §E, 2026-06-19)** — 80% distinguishes whole-file/near-whole replacement (100%, 90%) from a substantial-but-partial edit (a 20-line edit in a 200-line file ≈ 10%)).
- An **`Edit`-tool hunk that modifies < X% of the prior bytes is a partial edit and is EXCLUDED** — so a legitimate multi-file refactor (many small in-place edits) is **never nagged**.
- **A whole-file `Write` onto an existing file is destructive *regardless of tool name*** — this closes the full-file-`Edit` bypass (a single hunk that spans the whole file is functionally a full-overwrite and must count even though it presents as `Edit`, so the Write-keyed counter is not the sole trigger; the `(prior bytes, proposed bytes)` magnitude predicate above is what catches it).
- **Create vs overwrite split — on BOTH `Write` and `Edit` targets (R4-BL1).** A `Write` (or `Edit`) to a new path and to an existing path produce identical `tool_input` (there is no `exists` flag), so the hook **performs a `stat`/existence check on the target of both `Write` and `Edit` at hook time** to route the op — a `Write` **or** `Edit` whose target does **not** exist is a **create** (→ FR-11 create cap), a `Write` or `Edit` whose target **exists** is an **overwrite/edit** (→ this FR-38 destructive cap if it meets the magnitude predicate above). The split must cover `Edit` and not `Write` alone, because `Edit` creates files: an `Edit` with empty `old_string` on a non-existent path is the agent's file-create idiom, which would otherwise bypass the FR-11 cap (R4-BL1, live-reproduced — see FR-11). This existence check sits **inside the FR-26 residual-TOCTOU window already disclosed** (a path component could change between the `stat` and the agent's write); it is not a new sandbox gap.
- **`stat`-race cap-misroute — disclosed and bounded (R4-MA4); FR-40 is misroute-invariant.** Because the agent controls both writes, it can create a file *between* the `stat` and the destructive write so the `stat` reads "absent" and the op is **misrouted as a create** (FR-11 create cap, default 25) when it is in fact a destructive overwrite (FR-38 cap, default ~10) — or the reverse. The cap-accounting consequence (distinct from the FR-26 sandbox-escape property, which "not a new gap" addresses): the misrouted class can run against the wider of the two per-op caps before any per-op cap trips — **worst case the larger of the two per-op caps (~25) applies to the misrouted class**, a ~2.5× wider per-op silent band. **This cannot escape FR-40:** the per-turn files-touched cap (FR-40) increments on **both** the create-cap and the destructive-cap paths and counts **distinct files, not magnitude or routing**, so a misroute between FR-11 and FR-38 still increments FR-40 once per distinct file and is held at the FR-40 cap regardless of which per-op bucket the race chose. The "not a new gap" disclaimer applies only to the **sandbox boundary**, not to cap accounting — the two are different properties.

**Reachable destructive ops are archetype-specific (R3-BL1).** Under the Archetype-A (`claude -p`) deny-by-default matcher (FR-24), the only reachable file ops are **create / full-overwrite / partial-edit** — `delete`, `move`, `copy`, `rename`, and shell-`truncate` are all foreclosed by the Bash deny and are reachable **only in Archetype B** (where HoardPad owns the loop and executes the op itself). Consequently FR-38's `delete` counting (and `truncate` as a distinct shell op), FR-28's clobbering-move capture, FR-10(b)(ii)'s clobber confirm, and MA11's rename==move are **Archetype-B-only protections** — for Archetype A the FR-38 cap counts **overwrites only** (whole-file `Write`/`Edit` onto an existing file, plus the ≥X% magnitude predicate; a truncate-to-0 reaches Archetype A only as a `Write` of empty content onto an existing file, which the predicate already catches). **The mass-partial-edit / sub-threshold-overwrite injection class FR-38 does NOT cover (partial edits and `< X%` overwrites are excluded) is backstopped by FR-40, the per-turn files-touched cap (R4-BL2)** — NOT by FR-10(a). FR-10(a)'s writable-set count bounds blast radius by **how many files *exist*** in the root (it catches "you opened a 5,000-file tree"); it does **not** bound **how many files an injection *mutates***, because overwriting a file in place does not change the writable-descendant count — so on a normal medium root FR-10(a) never fires for a sub-threshold mass overwrite. The two controls are **orthogonal**: FR-40 bounds the aggregate "touch many files" attack; FR-10(a) bounds the existing-file blast radius. (A clobbering move/copy is Archetype-B-only and is already confirmed per FR-10(b)(ii); it is not double-counted here — see mi3 counting rule in §9.3.)

**Cap mechanics (MA12):** like FR-11, the cap **stays tripped after a confirm — no re-arm** (every further destructive op confirms; the counter is not reset), and for Archetype A the hook-side counter **accumulates across the agent's internal tool loop** within one `requestId` (verified in SPIKE-3) — and like FR-40 its no-re-arm tripped state **persists across continuation turns keyed to the user-initiated conversation**, not the per-invocation `requestId` (FR-40's *Cap-state lifetime* clause, R5-BL1). Exceeding the cap pauses for one confirm; per mi2 the `-p` realization is hook-deny-past-cap + a HoardPad-initiated continuation turn, not a literal pause/resume. **Cap integrity depends on the deny-by-default matcher (R3-MA3):** the FR-38 cap is only as strong as the matcher foreclosing every non-counted filesystem path — see FR-11's matcher-dependency note (a capped `-p` agent will attempt tool substitution; Bash and `AskUserQuestion` must both be denied). **Every overwrite onto an existing file also increments the FR-40 files-touched counter (R4-BL2)** — regardless of whether it meets the ≥X% magnitude predicate that gates *this* FR-38 cap — so a sub-threshold overwrite run that never trips FR-38 is still bounded on the aggregate axis by FR-40.
*Done when:* a scripted **Archetype-A** injection-defense fixture (poisoned README + benign prompt, e.g. "overwrite every `.cs` with a stub") performing more than the cap of overwrites — **including a variant that routes the overwrites through single-hunk full-file `Edit` calls (R3-BL1)** — is paused at the cap with a confirm, and the count of confirms shown is **asserted** (it must be ≥ 1, not 0, closing B5) for **both** the `Write`-overwrite and full-file-`Edit` variants; the separate **Archetype-B** fixture (e.g. "delete every `.md`") exercises the `delete` path through the shared file-ops service and is likewise paused at the cap; a turn of many ordinary partial edits (< X% each) performs them without nagging (FR-38 does not fire for partial edits); the create-vs-overwrite split is exercised by a `Write` to a new path (counts toward FR-11) vs a `Write` to an existing path (counts toward FR-38); the cap firing is recorded in the activity log with `downgradeReason: destructive-cap` (§9.3, MA13); **a turn that overwrites ≥ N distinct existing in-root files each sub-X% (tripping neither FR-38 nor FR-11) is held at the FR-40 files-touched cap (R4-BL2)** — see FR-40. Cross-referenced from FR-10, FR-11, FR-27, FR-40, NFR-10, NFR-3, C-4.

**FR-39 — Pending AI proposals surface (NEW 2026-06-14 round 2; BL1).** When an `approve-each` confirm (native or FR-10-downgraded) goes **unanswered** past the no-reply timeout (FR-24, default ~60 s), HoardPad **fails closed**: it denies the op, kills the `claude` process tree (NFR-8), and **parks the proposed operation in a pending-AI-proposals surface** — an area of the activity panel where each queued proposal is shown with its op type, target path(s), and **apply / discard** actions so the maintainer can act on it later. A short no-reply timeout is safe precisely because the op is recoverable from this queue (nothing is lost — the op simply did not apply). Every queued (failed-closed) op is appended to the activity log (FR-29 / §9.3, outcome reflecting the queued/denied state) so the queue is auditable. **What a queued proposal IS, and how it replays — Archetype-specific (R3-mi2).** For **Archetype A** the parked "proposal" is the **captured `tool_input`** (which fully describes the create/overwrite/edit the agent requested); the `claude` process was killed at the fail-closed, so applying the proposal later means **HoardPad executes that `tool_input` itself via its shared file-ops service — the Archetype-B execution path — NOT by re-launching `claude` or re-invoking the hook** (impossible without a live agent). This is benign because a PreToolUse-denied op left **no partial on-disk state**, so there is nothing half-written to reconcile. For **Archetype B** the proposal is the same captured tool-call, already an op HoardPad executes itself. In both cases applying a queued proposal later runs it through the full FR-26/FR-28/FR-29 path **as an Archetype-B op** (sandbox check + undo journal + activity log).
*Done when:* an `approve-each` confirm left unanswered past the no-reply timeout denies the op, kills the `claude` process tree, and shows the op in the pending-AI-proposals surface with apply/discard actions; the queued op appears in the activity log; applying it later executes the captured `tool_input` through the shared file-ops service's sandbox/undo/log path (R3-mi2) and discarding it removes it from the queue with a log entry; **the no-reply timeout is injected as a short test value (not the production ~60 s default), the way FR-24's minimum-version is injected, so the FR-39 test is fast and the boundary is not flaky (R3-mi12).** Cross-referenced from FR-24 (the approve-each fail-closed path) and FR-27.

**FR-40 — Per-turn distinct-files-touched cap (AI safety; NEW 2026-06-17 round 4; R4-BL2, Decision A; the aggregate primitive that bounds the sub-threshold-overwrite mass-corruption vector).** A single AI turn may touch at most a configured number of **distinct files** before HoardPad pauses and requires a one-time confirm to continue. This is the aggregate sibling of the per-op FR-11/FR-38 caps: where those bound an attack by *how much of each file* it changes, FR-40 bounds it by *how many files* it touches — the dimension a per-op X%-magnitude predicate cannot see, and the one a sub-threshold-overwrite injection ("replace the first `(X−1)%` of every `.cs` with a banner") exploits to corrupt an unbounded number of in-root files while tripping neither FR-38 (each op is an excluded partial edit) nor FR-11 (the targets already exist) nor FR-10(a) (overwriting in place does not change the writable-descendant count). *Default cap: **N = 20** distinct files per turn; tunable (FR-35); **MEASURED (SPIKE-3 §E, 2026-06-19)** — basis: same order of magnitude as the FR-11 create-cap band; targets the touch-many-files-sub-threshold attack; 20 distinct files in one turn without confirm is significant scope.*

**Mechanics — a hook-evaluable per-turn aggregate.** The hook maintains a **set of distinct file paths touched this turn** (canonical, resolved paths; the set is **owned by HoardPad and its lifetime is the user-initiated conversation / logical turn**, not the per-invocation `requestId`/`session_id` — see *Cap-state lifetime* below). It is incremented on **both** cap paths:
- **every create** (the FR-11 path — a `Write` *or* `Edit` to a non-existent target, including the `Edit`-empty-`old_string` create idiom, R4-BL1), and
- **every overwrite onto an existing file** (the FR-38 path — *regardless of per-op X% magnitude*, so a `< X%` sub-threshold overwrite that FR-38 deliberately excludes still increments FR-40).

When the count of distinct files touched reaches the per-turn cap **N**, the turn **pauses for a confirm** via the same downgrade-to-confirm machinery FR-38/FR-11 use (for Archetype A: the hook denies past the cap and "continue" is a HoardPad-initiated continuation turn, per mi2), recording `downgradeReason: files-touched-cap` (§9.3). Like the FR-11/FR-38 caps it **stays tripped after a confirm — the counter/set does NOT re-arm** (every further file touched confirms), so an injection cannot chain N-at-a-time through confirm-fatigue. **Counting rule:** a file counts toward FR-40 **once per turn** no matter how many times it is touched (it is a *set* of distinct paths), and the same op increments at most one *per-op* cap (FR-11 *or* FR-38, per the §9.3 mi3 disjointness rule) **and** the FR-40 set — FR-40 is an independent aggregate gate, not a re-count of the per-op caps.

**Cap-state lifetime — keyed to the user-initiated conversation, NOT the invocation (R5-BL1, Decision A, live-reproduced).** The FR-40 distinct-files-touched set **and** its no-re-arm tripped state (and, by the same rule, the FR-11/FR-38 no-re-arm tripped counters) are **owned by HoardPad and keyed to the user-initiated AI conversation / logical turn**, *not* the per-invocation `requestId`/`session_id`. Past the cap the hook can only **deny**, and "continue" is a **new** `claude -p` invocation HoardPad initiates (FR-11/mi2) — each invocation gets a **distinct `session_id`** and the hook process holds **no** cross-call memory (live-reproduced round 5), so an invocation-scoped counter would **re-arm** on every continuation and degrade the per-attack bound from *N distinct files* to *N files per one-click confirm*. HoardPad therefore mints a durable **conversation / logical-turn id** when the user initiates an AI conversation and **persists the FR-40 set + tripped state under it across every HoardPad-initiated continuation turn**: a continuation **resumes the same set** (a fresh `claude -p` invocation does **not** reset it); **only a new user-initiated conversation resets it.** The per-invocation `requestId` remains the per-op correlation / intra-invocation accumulation key (§9.3) — it is **not** the cap-state lifetime. (An invocation-scoped cap-state is explicitly **rejected** — it is the re-arm bug this clause closes.)

**(Residual — a pre-existing MA8 limit, not an FR-40 gap, R5-mi4.)** FR-40 counts a file touched many times in one turn **once** (the safe direction); an agent splitting a whole-file overwrite into **>50 sub-X% `Edit` hunks on a single file** ages out that buffer's earliest before-images under MA8 undo-retention (7 d / 50 ops per buffer, FR-28), so cumulative corruption of that one file is bounded by the surviving journal rather than by FR-40. Acknowledged; no new scope.

**FR-40 is misroute-invariant (R4-MA4).** Because it increments on **both** the create-cap and destructive-cap paths and counts **distinct files, not magnitude or routing**, a `stat`-race misroute between FR-11 and FR-38 (R4-MA4) cannot escape it — the file is counted once whichever per-op bucket the race selected. FR-40 is the single primitive that closes the sub-threshold-overwrite vector (R4-BL2), the `Edit`-create create-cap bypass (R4-BL1, which also increments FR-40), and the stat-race misroute (R4-MA4) together.

**Cap integrity DEPENDS ON the deny-by-default matcher (R3-MA3 class).** Like FR-11/FR-38, FR-40 is only as strong as the FR-24 matcher foreclosing every non-counted filesystem-effecting path — a capped agent will attempt tool substitution (`Bash`, `AskUserQuestion`, and any tool the matcher does not deny-by-default, R4-MA2), and the matcher must deny all of them or FR-40 is worthless. Verified in SPIKE-3.

*Done when:* a scripted turn that touches more than N distinct in-root files — **whether via creates, via full-file overwrites, or via sub-X% overwrites that individually trip neither FR-11 nor FR-38** — is paused at the FR-40 cap with a confirm-to-continue prompt, and the count of confirms shown is **asserted** (≥ 1, never 0); confirming lets HoardPad initiate a continuation turn and the cap stays tripped (no re-arm); **a continuation batch into the same conversation-keyed cap-state still confirms at the (N+1)th cumulative distinct file (no re-arm across the continuation, R5-BL1) — a fresh `claude -p` invocation resumes the same set rather than resetting it, and only a new user-initiated conversation starts a fresh set**; the cap firing is recorded with `downgradeReason: files-touched-cap` (§9.3); a sub-threshold-overwrite injection fixture (poisoned README + benign prompt, e.g. "replace the first few lines of every `.cs` with a banner") over N+ distinct files is **held at the FR-40 cap even though FR-38 and FR-11 alone do not fire** (R4-BL2, SPIKE-3); the FR-40 set is verified to increment on both the create path and the overwrite path and to be misroute-invariant under a `stat`-race ordering (R4-MA4, SPIKE-3). Cross-referenced from FR-10, FR-11, FR-27, FR-38, NFR-3, NFR-10, C-4.

**FR-28 — Undo of AI file operations.** Every captured AI file operation is undoable. Undo of an editor-buffer AI edit uses the standard Ctrl+Z edit history; undo of a filesystem AI op (create/copy/move/delete/overwrite) is reversible via an explicit "undo last AI file operation" action that restores prior filesystem state.

**Mechanism (minimum):** a **snapshot-before-write undo journal** — before applying any op, record the op type, paths, and a **prior-bytes snapshot**. **Durability ordering (M15):** the before-image blob (§9.4 `before/…bin`) and its journal entry must be written **and `fsync`'d to disk BEFORE the destructive op is allowed to mutate the target** — otherwise a crash between "target overwritten" and "before-image hit disk" leaves the original gone and the before-image torn, and undo would restore garbage. The destructive op is gated on the before-image's durable completion. Reversal: create → undo deletes the file *if it is unchanged since creation*; move → undo uses the recorded source+dest **and restores any clobbered-destination bytes** (see below); delete / overwrite → undo restores the recorded prior content (and path).

**Clobbering move/copy capture (Decision 1 / M10; rename==move, MA11).** When a `move`/`copy` proceeds onto an **existing** destination (only after the FR-10(b) confirm), FR-28 must capture the **clobbered destination's prior bytes** in addition to source+dest, so undo can restore the destination's original content (the earlier draft recorded only source+dest, silently losing the clobbered file's content). §9.4's `paths` carries `source`/`dest` and the journal records a before-image for the destination when it pre-existed. **A rename canonicalizes to `move`** (FR-26 op vocabulary, MA11), so a rename onto an existing file is captured the same way. **Rename-onto-open-dirty-tab fixture (MA11):** the AI renames `a.md`→`b.md` where `b.md` is **open in a dirty tab** — the test asserts (1) a clobber confirm fires (FR-10(b)(ii)) and (2) the dirty buffer for `b.md` is **reconciled** (conflict-prompted, per FR-19/§9.2 machinery), not silently orphaned under a destroyed on-disk file.

**Where undo CANNOT be guaranteed (stated explicitly) — and how the default mode never silently destroys (B4, reconciles C-4):**
- **(i) Uncaptured ops** — any `claude -p` write that bypassed interception, especially a `Bash` write. Deny-by-default tool gating (FR-24, FR-26) is what closes this gap; if interception is unavailable, only the degraded tree-snapshot mode applies (FR-26).
- **(ii) External modification (M14) — content hash is authoritative.** If a file was changed (by the user or another process) after the AI op but before undo, undo must **detect** the divergence and **refuse or warn** rather than clobber newer edits. The **content hash is authoritative** for the safety decision — `mtime` is used only as a cheap optimization to skip a re-hash, never as the sole basis (coarse mtime resolution — FAT 2 s, some network FS 1 s — lets a same-tick edit slip a mtime-only check, and a sync daemon touching mtime causes spurious refusal). To close the check→restore TOCTOU, the host **holds a file handle / re-verifies the hash immediately before the restore write**, not only at decision time.
- **(iii) Oversize files (cap) — confirmed BEFORE the op, never silent (B4/C-4 reconciliation); cap keyed on PRE-OP size (mi3).** Files beyond a configured snapshot size cap are not journaled, so undo is unavailable for that op. **The cap check uses the file's PRE-OP size, never the post-op size (mi3)** — otherwise a 9 MB→0-byte truncate-in-place looks "small" (post-op) and slips the cap, when the before-image that must be stored is the full 9 MB prior content. To satisfy C-4 ("every write undoable") in the default mode, an over-cap **overwrite, truncate, or delete is treated as an undo-unavailable op and is therefore *confirmed before it applies* under FR-10(b)** — it can never silently destroy an unrecoverable file in `auto-apply`. If the user confirms, the op proceeds, the activity log records that undo is unavailable, and (over-cap restore can never be attempted, since there is no `preOpContentHash`/before-image, per M14). The snapshot size cap is set high enough that ordinary edits are always journaled; the exact cap is a tech-design number.
- **(iv) Symlink-target overwrite — undo journals against the RESOLVED target (mi4).** When an in-bounds write goes through a symlink whose target is another in-root file (no escape, no FR-10 escape-block fires), the undo journal records the before-image and `preOpContentHash` against the **resolved target path**, not the link path — otherwise undo would restore against the wrong file. A fixture exercises an in-bounds symlink-target overwrite and asserts undo restores the resolved target's prior bytes.

**Undo-journal cross-session retention (MA8).** A buffer's undo-journal entries are retained **until that buffer is cleanly saved and closed**, after which its journal entries (and before-image blobs) are pruned. Across sessions, an entry that was never resolved by a clean save+close is retained for **7 days OR 50 ops per buffer, whichever comes first**, then pruned. This bounds disk growth while keeping "undoable" meaningful long enough to notice an unwanted op after a restart. Because an under-cap mass-delete (which is journaled and reversible) is now itself brought under the FR-38 destructive-op cap, it is **confirmed before applying** rather than relying solely on the user noticing and undoing before this retention window expires (closes the round-1 B5/M10 "silent under-cap delete" concern).

*Done when:* SC-5(b) passes; for a buffer edit, Ctrl+Z reverts it; for a file create, undo deletes the created (unchanged) file; for a move, undo restores the original location **and, if the move clobbered an existing destination, restores the destination's prior bytes**; for a delete, undo restores the file content and path; for an overwrite, undo restores the prior file content; an in-bounds symlink-target overwrite undoes against the **resolved target** (mi4); an undo attempted against an externally-modified file (detected by content hash, not mtime alone) warns/refuses instead of clobbering; an over-cap overwrite/truncate/delete is **confirmed before applying** (FR-10(b)) and then marked undo-unavailable (never silently destroyed); a crash injected **between the before-image write and the target overwrite** still recovers the original on undo (M15 durability-ordering test); a journal entry unresolved by a clean save+close is pruned after 7 days / 50 ops (MA8). The undo action operates in reverse order of the activity log.

**FR-29 — Activity log.** Every AI file operation (attempted and applied, including blocked/refused/queued ones) is appended to a viewable activity log. Each entry records: timestamp, the **effective** agency mode at time of op (`agencyMode` — the mode actually applied, e.g. `approve-each` when FR-10 downgraded an `auto-apply` op), the **configured** mode (`configuredMode`) and the **downgrade reason** (`downgradeReason`, MA13) so a downgrade/cap firing is provable, op type (read/create/copy/move/edit/delete/blocked), target path(s) via the `paths` object (carrying `target`/`source`/`dest`, **including the clobbered destination** for a clobbering move/copy), outcome (applied/blocked/undone/failed/queued), `backend` (`claude-cli` | `anthropic-api` | `local`), a `requestId` correlating all ops from one AI turn (the document standardizes on `requestId`; the phantom `sessionId` is dropped, mi6), `bytesBefore`/`bytesAfter` (size delta — **not** content), `undoRef` (pointer to the undo-journal entry, or a marker that undo is unavailable), `error` (sanitized reason when `outcome: failed`), `durationMs`, and — for `claude -p` — optional token/cost pulled from the agent's result message. **Never** logs API keys or file contents (NFR-7). **Append durability (M15/MA3):** the log is append-mostly, so NFR-4's whole-file temp+rename model (which covers only the *create* of line 1) is insufficient for in-place appends — see §9.3 for the **checksummed/length-prefixed NDJSON record** format and the "discard a torn trailing record on read" recovery rule that make a crash mid-append recoverable. This log is the only durable record of an undo-unavailable op (FR-28(iii)) and of a failed-closed queued op (FR-39).
*Done when:* SC-5(c) passes; the log is viewable in the UI; a blocked out-of-sandbox attempt (FR-26) appears with outcome `blocked`; an undone op (FR-28) is marked `undone`; a failed-closed queued op (FR-39) is recorded; a downgraded op records `configuredMode`/`agencyMode`/`downgradeReason` so the FR-10/FR-38 sign-off fixtures can assert the trigger (MA13); ops from one AI turn share a `requestId`; no entry contains an API key or file content; the log persists for the session and is written to a per-session NDJSON file under the app's data directory (§9.3); a fault-injection test that kills mid-append asserts the reader recovers all complete prior records and **truncate-repairs** the torn tail (MA3), and a **second case corrupts an interior (non-final) record and asserts no intact later record is dropped** (R3-MA2, per the per-record-`fsync` + truncate-repair model in §9.3).

### 6.7 Checklists (`.hoard`)

**FR-30 — `.hoard` checklist document type (amended, ODQ-11).** `.hoard` files open as an interactive checklist (not raw JSON) supporting **nested items up to three tiers** with add/edit/delete item, check/uncheck, drag-to-reorder, and **indent/outdent**. Deleting a **non-empty** parent prompts: **delete the whole subtree** (undoable) **vs delete the item and promote its children up one tier** (D8) — both branches are undoable and re-persist through the FR-31 write queue (zero-debounce terminal mutation; neither introduces a state-loss path; covered by the ODQ-10 in-list undo).
*Done when:* opening a `.hoard` file shows checkable, reorderable, **nestable** items; adding/editing/deleting items works; **indenting/outdenting an item moves it (and its entire subtree) between tiers** (depth cap honored, tier-4 indent is a no-op); deleting a non-empty parent prompts delete-subtree vs promote-children (both undoable); the on-disk format matches the §9.1 **v2** schema.
*Build note:* the checklist is a **custom Avalonia MVVM control** (`ItemsControl` + drag-reorder behavior, extended with tree ARIA semantics per ODQ-11 D11 — not a stock `TreeView`) — it does **not** involve AvaloniaEdit. This applies to FR-30 through FR-34, FR-41, FR-42.

**FR-31 — Durable auto-save on every mutation (serialized write queue, M13).** Every checklist mutation (add, edit text, check/uncheck, reorder, delete, mode change) is persisted to the `.hoard` file via an atomic write. To make "before the next mutation can begin" a real invariant rather than an assumption, persistence runs through a **single serialized async write queue per document** with **last-write-wins coalescing** (a burst of mutations collapses to one write of the final state, never out-of-order renames or partial states). Each write uses a **unique temp filename** in the target's directory (e.g. `.hoard.<ulid>.tmp`) so concurrent/retried writes never collide on a fixed temp name. **Debounce decision (MA7 — zero-debounce for TERMINAL mutations; honors C-5 literally).** `.hoard` mutations split into two classes:
- **Terminal (state-changing) mutations** — check/uncheck, reorder, delete, mode change, **and (ODQ-11) indent/outdent, collapse/expand-toggle, and delete-parent (both the delete-subtree and promote-children branches)**: **zero debounce.** Each is persisted **immediately** via the full atomic temp+rename+`fsync` sequence (NFR-4) before the next mutation can begin. There is no coalescing window for these, so a hard kill cannot lose a completed terminal mutation — this satisfies C-5's literal "never lose state on crash/close" for discrete checklist state (no C-5 weakening). The v2 schema (flat `items[]` + `parentId`/`collapsed`) keeps this invariant intact: still one flat array, one whole-file atomic rewrite per mutation.
- **Item-text keystrokes** — rapid edits to an item's `text`: coalesced like text buffers (FR-20), **default ≤ 150 ms** (then written), balancing zero-loss against per-write `fsync` cost. At most ≤ 150 ms of in-flight item-*text* keystrokes may be lost on a hard kill in the coalesce window — discrete check/order/delete state is never in that window. (Exact item-text coalesce window confirmed in tech-design / measured in SPIKE-1, §11.1.)

SC-6a is unchanged; its "last **completed** mutation" now equals "last **terminal** mutation" for the durability assertion.
*Done when:* SC-6a/SC-6b pass; after each mutation settles, the on-disk `.hoard` reflects the latest mutation before any later write begins; a process kill between writes never yields a corrupt or partially-written file (write-to-temp + atomic rename per NFR-4); a **rapid-mutation stress test** issuing N mutations faster than `fsync` latency ends with on-disk state == final in-memory state (no out-of-order or lost final write).

**FR-32 — Drag-to-reorder + keyboard indent/outdent (amended, ODQ-11).** Drag-to-reorder operates **within an item's sibling group** (same `parentId`); reordering renormalizes that group's `order`. **Keyboard indent/outdent is `Alt+Shift+←/→`** (D5): `Alt+Shift+→` demotes an item under its preceding sibling and `Alt+Shift+←` promotes it one tier, each carrying the item's **entire subtree** (D9). Pointer **drag-to-nest is out of v1** — deferred to v1.1; v1 pointer drag reorders within the current parent only. (`Alt+Up/Down` reorder within the sibling group is retained.)
*Done when:* dragging an item to a new position within its sibling group updates that group's `order` and rewrites the file; reopening preserves the order; `Alt+Shift+→` demotes an item under its preceding sibling (subtree travels), `Alt+Shift+←` promotes it one tier, both persist; the depth cap is honored (an indent that would push the item or any descendant past tier 2 is a no-op).

**FR-33 — Checked-item display modes (per-list, hierarchy-aware, amended ODQ-11).** Three per-list checked-item behaviors, selectable per checklist: `strikethrough-in-place` (**default** — checked item stays in position, shown struck through), `move-to-bottom` (checked items collected at the bottom of their sibling group), `hide-when-checked` (checked items hidden from view but retained in the file). Under nesting, the three modes treat **every checked item as done** uniformly. A checked **parent** moves/hides/strikes **as a whole block** — its subtree travels with it as a single contiguous unit (never splitting the subtree from its parent): under `move-to-bottom` the completed block sinks to the bottom of its sibling group; under `hide-when-checked` the whole block hides (retained in the file); under `strikethrough-in-place` the parent label is struck in place. A checked **leaf** moves/hides/strikes within its sibling group. The **hierarchy-aware display-index → stored-`order` mapping** for a drag in each mode is defined in §9.1 (M11) — applied per sibling group, treating a completed-parent block as one member of its group's partition — so the mapping back to stored `order` is explicit per mode (including how hidden items participate in drop-gap arithmetic under `hide-when-checked`, and the reverse-ordered-neighbors case under `move-to-bottom`).
*Done when:* the default new checklist uses `strikethrough-in-place`; switching a list to `move-to-bottom` relocates checked items (and a checked parent's **entire block**) to the bottom of their sibling group and unchecking returns an item to **its stored `order` position per §9.1** (not merely a "sensible" position); under `hide-when-checked`, checking a **parent** hides its **whole block** while preserving every item in the file (and a control reveals hidden/checked items); the selected mode is stored in the file (§9.1) and persists; the §9.1 hierarchy-aware display-index→stored-`order` mapping reproduces the **last-seen visible order per mode** (SC-6b extension); a property test covers drag-while-checked under each mode — sweeping **within nested sibling groups**, including a **checked-parent-block move/hide** — with the **specified §9.1 outcome** for each.

**FR-34 — New checklist creation.** The user can create a new `.hoard` checklist.
*Done when:* a "New Checklist" command opens an empty checklist tab; saving writes a valid §9.1-schema file; it participates in session restore (FR-19).

**FR-41 (NEW, ODQ-11) — Checklist nesting + completion-lock.** Items may be nested up to **three tiers** (depth 0/1/2) via `parentId` (§9.1 v2). **Checking a parent marks the whole block completed and locks its children:** while a parent is **checked**, its entire subtree is **inert** — descendants cannot be checked, edited, or reordered, and render visually disabled (greyed) **while still showing their own actual stored marks** (an unchecked child under a checked parent still displays unchecked, D3a — the "done" reading comes from the parent's check + completed treatment, not from faking child marks). An **unchecked parent leaves its children active.** A parent can be checked **manually at any time, regardless of child states** (D2a — the user's "this section is done" switch; not gated on children, not auto-derived, no cascade to child marks). Locking **does not mutate child state**: each descendant's `checked`/`text`/`order` is **retained** and restored **exactly** when the parent is unchecked (reopened). A node is interactive iff **all of its ancestors are unchecked** — formally `effectiveEnabled(item)` = every strict ancestor has `checked == false` (§9.1); the item itself stays toggleable so a completed parent can always be unchecked to reopen its block. Indent/outdent moves an item **with its whole subtree** (D9).
*Done when:* a descendant under a **checked** parent rejects check/edit/reorder and is announced "disabled" to assistive tech while still displaying its real check mark; **unchecking the parent reactivates the retained child state exactly** (no child state lost or altered by the lock/unlock cycle); a parent can be checked while its children are unfinished; indent/outdent carries the whole subtree; an indent past tier 2 (a fourth tier) is a no-op.

**FR-42 (NEW, ODQ-11) — Collapse/expand with durable state.** Parents render a ▸/▾ twisty that collapses/expands their subtree. Collapsed state is stored per item (`collapsed`, §9.1 v2) and persists across close/reopen as a **terminal mutation** (zero-debounce, FR-31).
*Done when:* collapsing a parent hides its subtree and persists immediately; reopening the file restores the exact collapsed/expanded layout last seen; toggling collapse survives an application kill (the `collapsed` write is a zero-debounce terminal mutation).

## 7. Non-functional requirements

**NFR-1 — Startup performance — MEASURED (SPIKE-1, 2026-06-19).** Cold start to interactive ≤ 1000 ms p90 (SC-1) **MEASURED PASS at 843.5 ms p90 (R2R-on, linux-x64; median 787.6 ms; ceiling 1265 ms)**; warm file open ≤ 250 ms p90 (SC-2) **MEASURED PASS at ≤ 209 ms p90 (upper-bound proxy; ceiling 313 ms)**. Both numbers were re-baselined on the reference hardware by SPIKE-1 and are now hard gates (win-x64 perf + native-Wayland leg Deferred; measured linux-x64/X11). Enabling mechanisms (design requirements, not optional): (i) **lazy per-language grammar registration** — a grammar is registered on first use of that language, not all 20 at boot (FR-7); (ii) **deferred subsystem init** — the AI provider, the Markdown preview renderer, and find-in-folder are constructed on first use, not at launch. The published binary is self-contained per-RID. **ReadyToRun is now a REQUIRED publish setting (`PublishReadyToRun=true` is MANDATORY for both RIDs), upgraded from the prior "may use, measured before committed" — SC-1 FAILS without it (R2R-off = 1309 ms p90).** Trimming is **optional** — perf-neutral with R2R-on and a size win (113 MB → 65 MB), but **only paired with R2R-on** (trim with R2R-off is counter-productive, +358 ms); trimming `TextMateSharp`'s embedded grammar resources is a known footgun, so if trim is enabled the grammar assembly's (and the FR-7 supplemental grammars') trim roots must be pinned. (`docs/tech-design.md` §1.1.)

**NFR-2 — Cross-platform parity.** Every FR builds and runs on both win-x64 and linux-x64 (§8 hard constraint). No Windows-only API on the default code path; OS-conditional shims are permitted only for genuinely platform-specific concerns (file watching, single-instance, subprocess launch) and must be surfaced in tech-design.

**NFR-3 — AI file-op safety.** The open-folder sandbox (FR-26) is non-negotiable: AI file writes never escape the resolved root; every write is undoable (FR-28) **or, where undo is unavailable (over-cap/clobbering ops), confirmed before applying (FR-10(b)/FR-28(iii)) so it is never silently destructive**; **in-bounds *mass* destruction is bounded by the per-turn destructive-op cap (FR-38), the per-turn create cap (FR-11), and the per-turn distinct-files-touched cap (FR-40)** — an injection attempting *mass* destruction (over any of those caps) hits a confirm rather than mutating silently, while a *small* in-bounds run (≤ all the caps) applies silently but remains recoverable (journaled/undoable/logged/MA8-bounded) — an explicit accepted posture (A-2/C-4), not a closed gap (R3-MA5). **FR-40 (distinct files touched, regardless of per-op magnitude) is the backstop for the sub-threshold-overwrite / mass-partial-edit class FR-38 excludes; FR-10(a)'s writable-set count is an *orthogonal* control that bounds blast radius by how many files exist, not how many an injection mutates (R4-BL2).** Every op is logged (FR-29). The FR-38 destructive cap counts ops per a hook-evaluable classifier predicate, and its reachable op classes differ by archetype (overwrites only for Archetype A; delete/clobbering-move added for Archetype B) — see FR-38/FR-26 (R3-BL1). Cap integrity itself depends on the deny-by-default matcher foreclosing substitute tools (R3-MA3, FR-11/FR-38/FR-40). Sandbox enforcement is path-resolution-based (canonicalize the target, verify it is the root or a descendant of the root after resolving symlinks), not string-prefix-based — **a residual TOCTOU window exists in Archetype A (observe-and-veto, M6) and is documented honestly in FR-26; Archetype B (HoardPad executes the op) is structurally stronger and TOCTOU-free.** For the `claude -p` archetype, these guarantees are **contingent on deny-by-default tool gating + interception being active** (FR-24, FR-26) — path-based checks cannot police shell writes, hence `Bash`/`mcp__*`/`MultiEdit`/`NotebookEdit`/`Agent` are all denied. **Fail-closed posture incl. hook-timeout-fail-open (MA1):** the CLI's hook timeout **fails open** (allows the write if the hook outlives its timeout), so the synchronously-blocking `approve-each` hook (FR-24/BL1) runs with no/long timeout and **HoardPad — not the hook timeout — owns cancellation** (kills the `claude` process tree on the confirm-dialog no-reply timeout and queues to FR-39); a "timed-out approve hook must not leak a write" test is in SPIKE-3. **Per-op liveness (MA14):** the hook must affirmatively confirm it armed each write; a mid-turn degrade blocks/confirms remaining ops or halts the turn (FR-10(c)/FR-26). If interception is infeasible, the only acceptable fallback is the **labeled degraded mode** (session-granularity tree-snapshot undo/log, FR-26), which **forces `approve-each`** (FR-10(c)) and never silently loses the guarantee. Per the SC-5 acceptance basis, the default backend is marked "Met" only under full per-op interception (verified on Linux; Windows subject to the Phase-4 parity spike + renegotiation clause); running in degraded mode caps SC-5/SC-8 at "Partial." **FR-10(a) specifically is now user-overridable, default ON (FS-5, docs/decisions.md DR-1)** — an OFF toggle narrows only the home/large-root confirm trigger; the sandbox boundary, the per-turn caps, and the undo/log guarantees this paragraph states are unaffected by the toggle in either state.

**NFR-4 — Durability (atomic-write sequence corrected, B2/B3/M16).** No data loss on ungraceful termination beyond the auto-save interval for text buffers (FR-20) and zero loss for `.hoard` mutations (FR-31, atomic write). Atomic writes use write-temp-then-rename **in the target's own directory**, with the **full ordered sequence** below (the earlier draft omitted the temp-file data `fsync`-before-rename step — on power loss the rename metadata could reach disk while the temp file's data blocks had not, leaving a zero-length/torn file under the real name with the old file gone):

1. **Write** the new content to a temp file (`.hoard.<ulid>.tmp` / equivalent) **in the same directory as the target** (M16 — same-FS is required for atomic `rename`; a `/tmp`-on-tmpfs temp renamed onto `/home` returns `EXDEV` and silently degrades to a non-atomic copy).
2. **`fsync` the temp file's data** so its bytes are durable *before* the rename.
3. **Atomic rename** the temp over the target.
4. On **Linux**, **`fsync` the containing directory** so the rename itself is durable.

**Windows primitives (B3 — two distinct paths, both write-through).** `System.IO.File.Replace` (wraps `ReplaceFile`) **throws `FileNotFoundException` when the destination is absent** and does **not** pass `REPLACEFILE_WRITE_THROUGH`, so it cannot be the single primitive the earlier draft assumed:
- **Create-when-absent path** (first-ever write of a new file — new `.hoard` via FR-34, first recovery snapshot of a never-saved scratch buffer, first activity-log / undo-journal write): write temp → `FlushFileBuffers` (or open with write-through) → **`MoveFileEx(temp, dest, MOVEFILE_WRITE_THROUGH)`** (MA4). `File.Move`/plain `MoveFile` to a fresh destination is **not** guaranteed atomic-durable on Windows the way POSIX `rename(2)` is — without `MOVEFILE_WRITE_THROUGH` the rename metadata can be lazily flushed, and `FlushFileBuffers` flushes only the temp file's *data*, not the move's directory metadata. `MoveFileEx` with `MOVEFILE_WRITE_THROUGH` fails if `dest` exists (correct for create-when-absent) and makes the rename durable. On **Linux**, the **step-4 directory `fsync` applies to the create path too** (MA4) — a crash after a rename-of-a-new-entry but before the dir-`fsync` can lose the new entry.
- **Replace-when-present path:** P/Invoke **`ReplaceFile` with `REPLACEFILE_WRITE_THROUGH`** (or `FlushFileBuffers` after) to get the write-through the PRD requires. Never a naive delete-then-move (which has a crash window with no valid file).

**Cross-device / network / synced targets (M16, reconciles §4.2 vs §9.1).** When the target is on a network/synced/cross-device filesystem where atomic `rename` is unavailable (`EXDEV`; SMB/NFS rename non-atomicity; Dropbox/Syncthing grabbing the temp mid-rename), HoardPad falls back to an **`fsync`'d in-place write + a warning that zero-loss atomicity is not guaranteed on this location**. **Plainly stated:** `.hoard` zero-loss (SC-6a) holds for **local same-filesystem** targets; on a Syncthing/Dropbox folder the temp+rename still runs in-directory, but full atomicity is best-effort and the warning is shown — the §9.1 overflow-bag defense protects against cross-*version* key loss on synced files, which is a separate concern from the atomic-write *crash* guarantee. A crash-injection / fault-injection test in tech-design power-cuts **between rename and dir-`fsync`** (and between temp-`fsync` and rename) and asserts **old-intact-or-new-complete, never torn**. **Scheduled tests (MA4):** this fault-injection suite explicitly **schedules the Windows first-ever-write (create-when-absent) crash-injection test** — power-cut around the `MoveFileEx(…, MOVEFILE_WRITE_THROUGH)` of a never-before-written file and assert the new file is either absent or complete, never zero-length/torn — alongside the Linux replace-path test. (Previously this Windows-create test was mentioned but never scheduled in §9/§11; it is now an explicit §11.1 durability-micro-spike item.)

**NFR-5 — Resource use — MEASURED (SPIKE-1, 2026-06-19).** Idle memory and CPU stay modest enough to leave the app open all day alongside other work. **Gate idle RSS ≤ 400 MB — MEASURED PASS: editor idle RSS 235.9 MB** (R2R-on, ~164 MB headroom); near-0% CPU when idle (no busy-poll loops). **"A handful of small docs" defined concretely (m1):** the RSS budget is measured with **10 docs of ≤ 50 KB each open, no folder opened, AI panel closed**. The `claude -p` child process is launched on demand and is short-lived per turn; its RSS **does not count** toward HoardPad's 400 MB idle budget (it is not running at idle) — **measured ~287 MB peak separately, not additive** with the editor's idle RSS. **Carry-forward:** the gate-comparable figure is the single-instance 235.9 MB; per-tab incremental RSS for a real multi-tab editor is **unquantified by the single-instance spike and is a Phase-8 measurement** against the m1 doc-set. Measured linux-x64 (win-x64 RSS Deferred). (`docs/tech-design.md` §1.3.)

**NFR-6 — Accessibility basics.** Keyboard operability for all primary actions (open/save/new/find/replace/toggle-preview/toggle-AI-panel/switch-tab); visible focus indication; **theme contrast meeting WCAG ratios — foreground vs background ≥ 4.5:1 for body/normal text and ≥ 3:1 for large or bold text** (same numeric basis as FR-37; replaces "sufficient contrast"). Full screen-reader certification is out of scope for v1 but no design choice may make later accessibility infeasible.

**NFR-7 — Security / privacy.** No telemetry; no network calls except to the user-configured AI backend (Anthropic API or local Ollama/LiteLLM endpoint; `claude -p` is a local subprocess). API keys and endpoints are stored in the per-user settings/data directory with file permissions restricted to the user where the OS supports it; keys are never written to the activity log or any shared file.

**NFR-8 — Reliability of AI subprocess.** The `claude -p` subprocess (default backend) must launch, stream, and terminate cleanly on both OSes; a backend that hangs or errors must not freeze the editor UI (AI requests run off the UI thread with cancellation). Cancellation **kills the whole process tree**, not just the launched process, because the agent may spawn children: on **Linux**, SIGTERM→SIGKILL to the process group; on **Windows**, a Job Object or `taskkill /T`. A HoardPad-owned wall-clock timeout plus `--max-budget-usd` and hook-side tool-call counting (FR-24 — note `--max-turns` does **not** exist in the CLI and was removed from the contract) bound a hung or runaway session. The Windows entrypoint may be a `claude.cmd` / `.exe` shim, so resolve an **explicit executable path** and launch with `UseShellExecute=false`. The process-tree kill is itself **unverified on Windows** (M7) and is part of the Phase-4 Windows interception-parity spike (§11).

**NFR-9 — Encoding & large-file behavior — threshold revised by SPIKE-1 (2026-06-19).** UTF-8 is the default encoding; existing files' encodings are detected and preserved on save. Files larger than a configured threshold may open with syntax highlighting/folding degraded for responsiveness. **SPIKE-1 found layout scales supra-linearly (282 ms@100 KB, 1.5 s@500 KB, ~12 s@5 MB), so the prior single 5 MB threshold is too permissive for the Markdown preview path.** The revised design is **SPLIT thresholds** (`docs/tech-design.md` §1.4): a **preview-render threshold ~100–200 KB** (above which the FR-15 rendered preview does not auto-render the full document) and a separate **editor syntax-highlight threshold ~500 KB** (above which the AvaloniaEdit live highlighter degrades, buffer still editable). **This is a directional, SINGLE-SAMPLE reading — Phase-8 confirms with a proper distribution and separates the preview-layout cost from the editor-highlight cost before the final pin** (OQ-5).

**NFR-10 — Prompt-injection posture.** All open-document and open-folder content delivered to the AI is treated as **untrusted data, never instructions**: it is supplied in the user/data channel and never concatenated into the system prompt. No content read from a file can be allowed to redirect agency. The sandbox (FR-26) is the hard backstop against *escape* — injection may waste a turn but cannot escape the resolved root. **In-bounds destruction is a separate threat (B5) addressed by the smart auto-downgrade default (FR-10/FR-11/FR-38/FR-40):** a poisoned in-folder file ("overwrite every `.cs` with a stub" / "delete every `.md`" / "replace the first few lines of every `.cs` with a banner") passes the sandbox (all writes in-bounds) yet would be destructive. Under the default `auto-apply`: **FR-38 caps per-turn destructive ops** (counted per its hook-evaluable classifier predicate, default ~10; the reachable destructive classes differ by archetype per R3-BL1 — overwrites for Archetype A, delete/clobbering-move added for Archetype B) — the round-2 fix that closes the gap FR-11 (creates only) left open; **FR-40 caps the per-turn count of distinct files touched** (default N; increments on both the create and overwrite paths regardless of per-op magnitude, R4-BL2), which is what **backstops the mass-*partial-edit* / sub-threshold-overwrite class FR-38 deliberately excludes**; **FR-10** forces a confirm for irreversible/clobbering ops and on a home/large root (whose file-count counts the **true writable set**, FR-10(a)/MA9 — a control that bounds blast radius by *how many files exist*, **orthogonal** to FR-40's *how many an injection mutates*, R4-BL2; FR-10(a) does **not** backstop the excluded class); and **FR-11** caps per-turn mass-create.
**Honest scope of the confirm wall (R3-MA5, bounded on the aggregate axis by FR-40 per R4-BL2).** An injection attempting ***mass*** destruction — more than the ~10-destructive or ~25-create per-op caps, **or more than N distinct files touched (FR-40)** — hits a confirm (an obvious red flag) rather than silently mutating disk. A ***small*** in-bounds destructive run (≤ the caps — e.g. an injection that overwrites or deletes 9 files, **or a sub-threshold overwrite run that stays under the FR-40 files-touched cap**) applies **silently** under `auto-apply`, **but remains journaled, undoable, logged, and bounded by undo-retention (MA8)** — an **explicit accepted, eyes-open posture (A-2/C-4)** for a solo personal tool, **not a closed gap**. **The sub-threshold-overwrite band is NOT unbounded (R4-BL2):** because FR-40 increments on every overwrite regardless of per-op X% magnitude, a sub-X% overwrite run applies silently-but-recoverably **only up to the FR-40 files-touched cap**, above which it confirms — closing the previously-unbounded "corrupt the leading `< X%` of an arbitrary number of in-root files with zero confirms" path. **This bound holds across the `claude -p` continuation turn (R5-BL1):** the FR-40 set + no-re-arm state persist under HoardPad's conversation / logical-turn key (FR-40 *Cap-state lifetime*), so a continuation **resumes the same set rather than re-arming the cap** — the per-attack bound is N distinct files, **not** N-per-confirm (an invocation-scoped counter would re-arm on each HoardPad-initiated continuation and is explicitly rejected). (This replaces the prior absolute "an injection that tries to do real damage hits a wall of confirms" claim, which was false for the under-cap band — the BL4 internal-honesty discipline applied to the agency surface.) This reconciles the `auto-apply` default with this threat model: silent apply is reserved for in-bounds, reversible, recoverable, scoped ops below **all** the per-turn caps (per-op FR-11/FR-38 *and* aggregate FR-40); mass destruction above any cap confirms. **Cap integrity depends on the deny-by-default matcher foreclosing substitute tools (R3-MA3):** a capped `-p` agent will attempt `Bash`/`AskUserQuestion` substitution (and any tool the matcher does not deny-by-default, R4-MA2), all of which the matcher denies (FR-11/FR-38/FR-40). A scripted poisoned-README fixture (FR-10 / FR-38 / **FR-40** Done-when, B5) **asserts the number of confirms shown is ≥ 1** (never 0) for the *over-cap* sign-off record — **including the sub-threshold-overwrite variant that trips only FR-40 (R4-BL2)**.

**Read-side document-content scrub is an ACCEPTED, DOCUMENTED residual for v1 (DR-DS-4, maintainer decision 2026-07-17).** The DragonScrub run (2026-07-16) scrubs the two text paths HoardPad itself composes — outbound settings-marker redaction (DS-3) and the inbound QA4-12 transcript re-injection sink (DS-5, `Engine.ScrubInput`) — but the default Archetype-A backend (`claude -p`) reads document files **itself from disk** via its own native `Read` tool, on a path HoardPad only *gates for write-safety*, never *inspects for content* (`MultiDocContextDescriptor` carries paths+flags only, NG-4). So an injection payload embedded in a file the CLI reads reaches the model **un-scrubbed** — DragonScrub never holds those bytes. **This does NOT weaken this posture:** it is a *quality/trust* residual on *untrusted file content*, **not a containment gap** — every write remains structurally gated by the deny-by-default hook + per-turn caps + `SandboxPolicy`, none of which trust prompt or file content, so the injection can at most waste a turn or steer non-write behavior, never escape the root (as this section already establishes). For personal-first, single-user, local v1 (the files are the user's own) this residual is accepted and documented rather than closed with a protected-spine change. **Reversible:** the DS-7 escalation (`docs/escalation-inbound-doc-content-scrub.md`) records the reopen path if the threat model tightens (shared/multi-user, untrusted third-party ingest, hosted posture) — **Q-CAP is SUPPORTED**, so the preferred fix is an in-hook **PostToolUse** scrub leg returning `updatedToolOutput` (cheaper than a full App-mediated read tier), gated by the full protected-spine review + SC-5 re-verify when built.

## 9. Data formats

### 9.1 `.hoard` checklist schema

`.hoard` files are UTF-8 JSON. The schema is versioned to allow forward migration. Atomic write (temp + rename) on every mutation (FR-31).

```json
{
  "schemaVersion": 2,
  "title": "Trip",
  "settings": {
    "checkedItemMode": "strikethrough-in-place"
  },
  "items": [
    {
      "id": "01J9Z8K3QX5N7B2D4F6H8K0M2P",
      "text": "Trip",
      "checked": true,
      "parentId": null,
      "order": 0,
      "collapsed": false
    },
    {
      "id": "01J9Z8K4RT9C1E3G5J7L9N1Q3S",
      "text": "Flights",
      "checked": false,
      "parentId": "01J9Z8K3QX5N7B2D4F6H8K0M2P",
      "order": 0,
      "collapsed": false
    },
    {
      "id": "01J9Z8K5SV0D2F4H6K8M0P2R4U",
      "text": "Hotel",
      "checked": false,
      "parentId": "01J9Z8K3QX5N7B2D4F6H8K0M2P",
      "order": 1,
      "collapsed": false
    },
    {
      "id": "01J9Z8K6TW1E3G5J7L9N1Q3S5V",
      "text": "Packing",
      "checked": false,
      "parentId": null,
      "order": 1,
      "collapsed": false
    }
  ]
}
```

**Schema is a flat `items[]` array — hierarchy is derived, not nested (D1, ODQ-11).** Nesting is expressed by `parentId` + per-sibling-group `order`; the file is never a nested tree. This preserves the FR-31 single flat-array write queue, the `[JsonExtensionData]` round-trip, and the atomic temp+rename whole-file rewrite **unchanged** — `parentId`/`collapsed` are ordinary typed fields.

Field contract (v2):

| Path | Type | Required | Rules |
|---|---|---|---|
| `schemaVersion` | integer | yes | Current = **`2`**. Readers reject unknown **higher** versions with a clear message rather than silently misparsing (unchanged rule). A `schemaVersion: 1` file loads via the v1→v2 migration rule below. |
| `title` | string | yes | Display title of the checklist; may be empty string but key must be present. |
| `settings.checkedItemMode` | enum string | yes | One of `strikethrough-in-place` (default), `move-to-bottom`, `hide-when-checked` (FR-33). |
| `items` | array | yes | May be empty. A **flat** array; nesting is derived from `parentId` (no nested-tree JSON). |
| `items[].id` | string | yes | Stable unique id per item, **generated as a ULID** on creation (sortable; embeds creation time). GUID is accepted on read for legacy/foreign files but never newly written. Never reused or reassigned on reorder/indent/outdent. |
| `items[].text` | string | yes | Item label. May be empty string transiently while editing; persisted as-is. |
| `items[].checked` | boolean | yes | Check state. `checked` means **"completed"** for **every** item, leaf or parent (one uniform meaning, D2). On a **parent** it *also* locks the subtree inert (FR-41 completion-lock); the schema stores a single `checked: bool` with this one meaning. |
| `items[].parentId` | string \| null | yes (default `null` on absence) | **NEW (v2).** `null` = a top-tier (tier-0) item. Otherwise the `id` of the parent item. Must reference an existing item; **no cycles**; **no dangling** references. A dangling **or** cyclic `parentId` is **repaired to `null` on load with a logged note** (the item promotes to tier 0 rather than rejecting the file). Default on absence = `null`. |
| `items[].order` | integer | yes | 0-based position **within the item's sibling group** (the set of items sharing the same `parentId`), contiguous `0..n-1` per group (no gaps). **Display order is a pre-order walk:** for each sibling group, items by `order` ascending, descending into each item's children before the next sibling. The `move-to-bottom`/`hide-when-checked` modes are display transforms layered over this pre-order walk, not mutations of stored `order` (unchecking/un-hiding returns an item to its stored sibling-group position). |
| `items[].collapsed` | boolean | yes (default `false` on absence) | **NEW (v2).** View state of a parent's subtree (▸ collapsed / ▾ expanded). Meaningful only for items with ≥1 child; preserved-but-ignored for leaves. Default on absence = `false`. Toggling it is a **terminal mutation** (zero-debounce, FR-31/FR-42). |

**Derived invariants (pure functions in `HoardPad.Core.Checklist`, C-9; no on-disk field).** None of these are persisted — all are computed from the flat `items[]` + `parentId`:

- **`depth(item)`** = strict-ancestor count. **Max = 2** (tiers 0/1/2 — three tiers, D4). An indent that would push an item **or any descendant** past tier 2 is a **no-op** (quiet signal, no mutation, no error).
- **`isParent(item)`** = has ≥1 child; **`isLeaf(item)`** = 0 children. `checked` is **"completed"** uniformly for every item; on a parent it *also* locks the subtree (FR-41).
- **`effectiveEnabled(item)` = every strict ancestor of `item` has `checked == false`** (a tier-0 item, having no ancestors, is always enabled). A node is interactive — its check/text/order may be mutated — **only while all of its ancestors are unchecked**; checking **any** ancestor locks it (renders disabled/greyed, FR-41). **The item itself stays toggleable regardless of its own `checked` state** (so a completed parent can always be unchecked to reopen its block). This is a pure ancestor-chain function and the sole driver of the FR-41 inert/greyed state; it never mutates child state. (Identical contract wording in architecture §6.5 and tech-design §5.7.)
- **Sibling-group renormalize** — after any reorder/indent/outdent/delete, each affected sibling group is renormalized to contiguous `order` `0..n-1`. The whole-file-rewrite + atomic temp+rename (FR-31/NFR-4) is unchanged.

**Hierarchy-aware reorder-vs-display-mode semantics (correctness invariant, FR-32/FR-33) — with the explicit display→stored mapping (M11, hierarchy-aware per ODQ-11).** Drag-to-reorder operates on the **stored-order** sequence **within an item's sibling group** (same `parentId`): a drag computes the item's new stored `order` within its group, then **that sibling group** is renormalized to contiguous `0..n-1`. The display-mode view transform (`move-to-bottom` / `hide-when-checked`) is recomputed **after** the stored mutation — never the reverse. This preserves the invariant "unchecking/un-hiding an item returns it to its stored sibling-group position." **The mapping is now applied per sibling-group (the partition dimension), within the pre-order display walk.** Because the user drags in the **displayed (transformed)** order, the **display-index → stored-`order` mapping** is defined explicitly per mode so FR-33's outcome is testable, not "sensible".

**Hierarchy-aware display-index → stored-`order` mapping rule (binding, identical wording in architecture §6.5 and tech-design §5.7).** Within each sibling group, a **completed parent** (an item with `checked == true` that has children) is treated as a **single contiguous unit**: under `move-to-bottom` its **whole block sinks** to the bottom of its sibling group, and under `hide-when-checked` its **whole block hides** — the block (the parent and its entire subtree, by the pre-order walk) moves or hides as one unit, never splitting the subtree from its parent. A completed **leaf** moves/hides within its sibling group as before. The per-mode arithmetic below is applied **once per sibling group**, with the completed-parent-block treated as a single member of its group's partition:

- **`strikethrough-in-place`:** display order == stored order within each sibling group; a drop at display gap *g* maps directly to stored `order = g` in that group.
- **`move-to-bottom`:** the display is `[unchecked items in stored order] ++ [checked items in stored order]`. A drop **between two visible neighbors** maps to the stored `order` strictly between the neighbors' stored `order` values **within the same display partition** (unchecked-region drops stay among unchecked stored positions; checked-region drops stay among checked stored positions); the dropped item's `checked` state is unchanged. **Reverse-ordered-neighbors case:** if the two visible neighbors are not adjacent in stored space (the partition reordered them), the target stored `order` is the value immediately after the upper neighbor's stored `order`, then renormalize — i.e. the upper neighbor wins as the anchor (deterministic, not "between two reverse-ordered points," which has no coherent single target). **Partition-edge cases (mi9), each with a defined stored target:**
  - **No-upper-neighbor (drop at the very top of a partition):** target stored `order` is the value immediately **before** the lower neighbor's stored `order` within that partition (the lower neighbor is the anchor), then renormalize.
  - **No-lower-neighbor (drop at the very bottom of a partition):** target stored `order` is the value immediately **after** the upper neighbor's stored `order` within that partition, then renormalize.
  - **Partition-boundary drop (between the last unchecked and the first checked item):** the drop resolves to the **end of the unchecked partition** if the dragged item is unchecked, or the **start of the checked partition** if it is checked — the dragged item's `checked` state, not the pixel, decides which partition it joins (a dragged item never silently changes `checked` state via a boundary drop).
  The FR-33 property test asserts the **specific resulting visible position** for a reverse-ordered drop (not merely "deterministic"), so "upper-neighbor wins" is verified to render where specified.
- **`hide-when-checked`:** hidden (checked) items are absent from the display but **retain their stored `order`**. A drop at a visible gap maps to the stored `order` of the visible item **after** the gap (or end-of-list); hidden items keep their stored positions and are **renormalized along with** the visible ones after the move (so a later un-hide returns each item to a contiguous, stable position). Drop-gap arithmetic counts only visible items for the gap index, then translates to stored `order` via the visible→stored index map.

**Collapsed-parent rule for the visible-row sequence (Gap B, binding across all three modes).** Collapse is **orthogonal** to the checked-item display mode but feeds the **same visible-row sequence** the display-index / drop-gap arithmetic runs over. The consistent reading: **a collapsed parent's descendants are absent from the visible-row sequence** — the same idiom as hidden-checked items — for display-index and drag-drop-gap arithmetic, **regardless of the parent's `checked` state** (this includes a *collapsed-but-unchecked* parent: its children are present in the file and active, but are not visible rows while collapsed). The **collapsed parent itself remains a visible row** and still participates in its sibling group's partition arithmetic (it can be dragged, checked, etc.). **Expanding restores the parent's descendants to the pre-order walk at their stored positions** (their `parentId`/`order` were never mutated by collapse — collapse only toggles `collapsed`, FR-42). Combined with the completed-block rule above: a *checked* parent hides/moves **as a whole block** (subtree travels), whereas a *collapsed-but-unchecked* parent's children are merely **not rendered** while its own visible row stays in place and active — these are distinct, composable behaviors over the one visible-row sequence.

This mapping is a pure function in the shared domain (C-9); the property test (tech-design owns it) covers **drag-while-checked under each of the three modes with the specified stored-`order` outcome above** (FR-33), **and the collapsed-parent visible-row rule (Gap B) including a collapsed-but-unchecked parent**.

**Durability + unknown-key round-trip + DETERMINISTIC serialization (M12).** Every mutation rewrites the whole file via temp-write + atomic rename in the target's directory (NFR-4); a crash mid-write leaves the prior valid file intact (SC-6a, NFR-4). Because the whole file is rewritten on every mutation, preserving unknown/extra keys is **not** best-effort — the deserializer captures unknown keys in a JSON **overflow bag** (`[JsonExtensionData]`) at both object levels (root and per-item) and re-emits them on write. Without it, every mutation silently drops keys a newer build wrote — a real cross-version data-loss path, since the maintainer syncs two machines by their own means and an older build can reopen a file a newer build authored. The overflow bag is therefore **required**.

**Deterministic, diff-stable serialization (M12 — matters for the maintainer's synced files; "byte-identical" scoped honestly per MA2; CONFIRMED by SPIKE-5, 2026-06-19).** `System.Text.Json` stores extension-data values as `JsonElement` and does **not** guarantee byte-identical numeric re-emission or stable key ordering; left unspecified, two slightly-different builds re-emitting the same logical file produce noisy diffs and **fight over formatting on a synced folder (two-machine formatting wars / sync conflicts)**. **SPIKE-5 (§0) re-confirmed MA2 against the .NET floor** — numbers ARE byte-stable (overflow-bag `JsonElement` raw-text); unicode escaping and cross-version key ordering are NOT — and the tech-design decisions below are now PINNED (full contract in `docs/tech-design.md` §3):
- **Numbers ARE safe.** `JsonElement` preserves raw number text verbatim (`1.50`, `1E10`, 64-bit ints, `-0.0` all round-trip exact), so the number leg the PRD most worried about holds. **Scope of the raw-text guarantee (mi11):** raw-text preservation applies only to **overflow-bag (`JsonElement`) values**; **typed** fields (`int order`, `int schemaVersion`) are normalized by STJ's number writer — which is **fine**, because HoardPad controls their encoding and emits them canonically. The determinism claim is scoped to bag values vs typed fields accordingly.
- **"Byte-identical" is NOT a universal invariant (MA2).** Two legs cannot be made byte-stable: (a) **unicode escaping** — the default encoder escapes `<`→`<` and uppercases `é`, while `UnsafeRelaxedJsonEscaping` emits literal `é`, so a file authored with one form is not byte-identical after a re-save in the other; (b) **cross-version key ordering** — `[JsonExtensionData]` forces all unknown keys *after* all known keys, so a key a newer build interleaves between known properties relocates to the tail on an older build's re-save. The invariant is therefore restated: **serialization is byte-identical for files already in HoardPad's canonical form; the first re-save of a foreign/older-form file canonicalizes it (an accepted one-time diff), and is byte-identical on every save thereafter.**
- **Pinned encoder + unicode canonicalization rule — PINNED (tech-design §3.2(a)): `JavaScriptEncoder.UnsafeRelaxedJsonEscaping`, emit literal non-ASCII**, stable across all HoardPad builds and both RIDs. Rationale: `.hoard` is a local personal JSON checklist (never an HTML-attribute context, so the default encoder's HTML-injection escaping is irrelevant) synced/diffed by the maintainer's own means — literal `é`/`<` produces the smallest, most human-legible diffs. ("Unsafe" refers to HTML-injection contexts, which do not apply here — not a security relaxation.) Within-bag insertion order **IS** preserved (good); only the known/unknown **boundary** relocates.
- **Interleaved-new-key relocation — PINNED (tech-design §3.2(b)): `[JsonExtensionData]` overflow bag + accept the one-time canonicalizing diff.** The custom raw-key-order converter (zero relocation) is **NOT** shipped in v1 — `[JsonExtensionData]` is the simpler, lower-risk mechanism (one STJ attribute; preserves unknown keys + within-bag order), and its only cost is the one-time known/unknown-boundary relocation diff on an older build's first re-save (recoverable, non-data-losing, byte-stable thereafter), not worth the converter's complexity for a single-user tool. The converter remains the documented upgrade path (OQ-TD-2, tech-design §7) if two-machine sync friction ever warrants the absolute no-spurious-conflict guarantee.
- **Fixed property ordering** — known properties emitted in a fixed declared order; overflow-bag keys emitted in their preserved within-bag insertion order.
- **Round-trip fidelity test (required, scoped):** parse → re-emit is **byte-identical for a file already in canonical form**, over a corpus covering integers, large/64-bit integers, decimals, nulls, nested objects, and unicode strings at **both** object levels; a separate test asserts the **first** re-save of a non-canonical file produces the documented one-time canonicalizing diff (not a data-loss).
- **Known-key-promotion migration rule:** when a key that was previously unknown (carried in the overflow bag) becomes a **known property** in a later `schemaVersion`, the migration **promotes** the overflow-bag value into the typed property (and removes it from the bag) on read of the older file, so the value is not duplicated across both the typed field and the bag; tech-design defines the per-key promotion mapping at each `schemaVersion` bump.

**Depth-cap-on-import clamp (ODQ-11 risk 4, binding).** Loading or pasting/importing a structure deeper than three tiers does **not** reject the file — it **clamps**: any item whose derived `depth` exceeds 2 is **reparented up to tier 2** (the overflow is flattened to tier 2, i.e. re-pointed to the deepest still-legal ancestor), with a logged note. Combined with the dangling/cyclic-`parentId`-repaired-to-`null` rule above, no structural irregularity in a foreign/hand-authored file can make `.hoard` unreadable; the depth cap (D4) is enforced on import as well as on interactive indent.

**Worked clamp example (pinned expected result for the test fixture).** Imported structure (six items; `A` at tier 0, `B` under `A` at tier 1, `C` under `B` at tier 2, and two depth-3 cousins `D`+`E` both under `C`):

| id | imported `parentId` | imported depth | clamped `parentId` | clamped depth |
|---|---|---|---|---|
| `A` | `null` | 0 | `null` | 0 |
| `B` | `A` | 1 | `A` | 1 |
| `C` | `B` | 2 | `B` | 2 |
| `D` | `C` | 3 (overflow) | **`B`** | **2** |
| `E` | `C` | 3 (overflow) | **`B`** | **2** |

The two depth-3 cousins `D` and `E` are each **reparented to the deepest still-legal ancestor** — their grandparent `B` at tier 1, making them tier-2 siblings of `C` — rather than dropped, rejected, or promoted to tier 0; their relative sibling `order` within the new group is renormalized contiguous. (Had `C` itself been at depth 3, it too would clamp to its deepest legal ancestor; the rule is applied bottom-up so the deepest-legal-ancestor of an overflowing item is always already within the cap.)

**v1 → v2 migration rule (ODQ-11 D10, binding).** On reading `schemaVersion: 1`: set `parentId = null` and `collapsed = false` for every item (every item becomes a tier-0 leaf), and keep each item's `order` as its tier-0 sibling order; the **first re-save emits `schemaVersion: 2`**. Absent `parentId`/`collapsed` on any file (foreign/hand-authored) default the same way (`null` / `false`). Readers still reject unknown **higher** versions per the rule above. **Because HoardPad has not shipped (Phase 8 is the build), there is no deployed v1-reader population — the version bump is effectively free**; the v1→v2 load rule exists only for robustness on hand-authored/foreign flat files.

### 9.2 Session-state persistence shape

Session state persists to a flat-file store under the app's per-user data directory, rewritten on graceful close and refreshed by auto-save (FR-19, FR-20). **An embedded SQLite store was explicitly considered and rejected** as over-engineering for a single-user, single-process personal tool — the flat-file design below carries no concurrency burden and adds no dependency.

**Recovery-directory-as-source-of-truth — MACHINE-LOCAL (R4-MA1, Decision A).** The recovery directory is stored under the **per-machine app-data dir and is NOT synced** — the maintainer syncs their notes folders, not the application data directory. Recovery snapshots therefore never cross machines; the cross-machine duplicate-`tabId` scenario cannot occur for snapshots, and the per-machine `seq` below is a *same-machine* tie-break (see the tie-break edge cases). To eliminate the only multi-file consistency hazard, each recovery snapshot is **self-describing** — it embeds its own `tabId`, `path`, `kind`, `cursor`, `savedAt`, and a **monotonic per-machine sequence counter** (`seq`, incremented on every snapshot write on that machine — the same-machine crash-mid-write tie-break primary key, R3-MA1 (MA6+MA10)) — and the **recovery directory is the source of truth**. `session.json`'s `recoveryRef` is demoted to a **rebuildable index/hint**, not a foreign key; `session.json` entries carry the same `seq` value at their last persist so `path` authority can follow the more-recently-persisted of {snapshot, session-entry} (R3-MA1 (MA6+MA10)).

**`tabId` is the durable correlation key.** The single stable join between a session tab and its recovery snapshot is `tabId` — the value embedded inside each self-describing snapshot, which equals the session tab `id`. Snapshot **filenames are opaque** and are never used as the join key (a renamed or relocated snapshot still joins by its embedded `tabId`).

**Reconciliation rule (pure domain logic; directory enumeration is the host's job) — 3-DIMENSIONAL table (B6, replaces the non-exhaustive 2×2).** The earlier 2×2 over `{snapshot, session-tab}` dropped the **on-disk file** dimension and contained silent-loss cells. There are **three** independent dimensions:
1. **Snapshot present?** (a self-describing recovery snapshot for this `tabId` exists / absent)
2. **Session-tab present?** (an entry in `session.json` for this `tabId` exists / absent)
3. **On-disk file state at `tab.path`** (for `kind: file`/`hoard`): **present-unchanged** / **present-changed-externally** / **deleted** (compared against the snapshot's recorded hash+mtime, per B7/FR-19 — content **hash** is authoritative for this comparison; `mtime` is only a cheap re-hash-skip optimization, **never** the sole basis, per FR-28(ii)/FR-19, so clock skew or a sync-daemon mtime touch cannot re-enter as a false-unchanged verdict). (For `kind: scratch` there is no on-disk file; dimension 3 is N/A.)

Every cell is defined:

| Snapshot | Session-tab | On-disk file (kind:file/hoard) | Action |
|---|---|---|---|
| present | absent | present-unchanged | Recover as **orphan tab** from snapshot metadata; buffer = snapshot bytes; no conflict (disk matches snapshot baseline). |
| present | absent | present-changed-externally | Recover as orphan tab but **surface a conflict** (keep-recovered / keep-disk / diff, per FR-19) — never silently arm a clobbering Save. |
| present | absent | deleted | Recover as orphan tab marked **"on-disk file deleted"**; the tab opens with the recovered buffer but is treated as **unsaved-to-a-missing-path** (next Save is a re-create, prompted), not a silent resurrection of a deliberately-deleted file. |
| present | present | present-unchanged | **Join on `tabId`**; snapshot supplies buffer bytes + cursor. |
| present | present | present-changed-externally | Join on `tabId` but **surface a conflict** (FR-19) — the recovered buffer vs newer disk; do not silently restore + arm a clobbering Save (B7). |
| present | present | deleted | Join on `tabId`, buffer from snapshot, tab marked **"on-disk file deleted"** (as above — next Save is a prompted re-create, not silent resurrection). |
| present | present (scratch) | N/A | Join on `tabId`; restore scratch buffer from snapshot. |
| absent | present | present (file/hoard) | **Keep** the tab; reopen from disk (no unsaved content to recover). |
| absent | present | deleted | **Drop** the tab (its file is gone and nothing was unsaved) — or, if `isDirty` was recorded true but no snapshot survives, surface "unsaved content for a now-deleted file could not be recovered." |
| absent | present (scratch) | N/A | **Drop** it (a scratch buffer with no recoverable content). |
| present | absent (scratch) | N/A | Recover as orphan **scratch** tab from snapshot. |
| absent | absent | — | Nothing. |

> here for historical record only; it no longer drives production behavior. `session.json` no longer
> persists `openFolder`/`canonicalOpenFolder` as the source of truth for the next launch's AI sandbox root —
> the root (== the folder-panel root == the AI write root, ONE root, never two) is instead **recomputed

**Open-folder dimension (MA5 — SUPERSEDED, see above — the AI sandbox root is reconciled, not just the tabs).** `session.json` carries `openFolder` (the AI sandbox root, FR-26), but the table above reconciles only *tabs*. On restore the open folder is reconciled as a **separate dimension**, because the sandbox root is safety-critical — silently arming AI write agency on a stale path is unacceptable (the maintainer's cross-machine sync workflow can move/delete/rename the folder while the app is dead):
- **Present-unchanged** (the prior `openFolder` resolves to the same existing directory): restore it as the open folder; AI write agency arms normally (subject to FR-10(a)'s home/large-root downgrade re-evaluated against the current writable-set count).
- **Moved / renamed / changed** (the prior `openFolder` no longer resolves, or resolves to a different directory): **restore the tabs, but DO NOT silently arm AI write agency on a stale or guessed root.** HoardPad **re-prompts the maintainer to confirm or re-pick the AI root before write agency arms** — until they do, the panel runs read/chat only (per FR-26's no-folder rule, which disables AI file-write agency when there is no resolved open folder). No silent stale sandbox root.
- **Deleted / absent:** as "moved/changed" — tabs restore, AI write agency stays disabled until the maintainer picks a root.
- **Tab path resolves outside the restored open folder (MA5):** a restored tab whose snapshot `path` now resolves **outside** the (re-confirmed) `openFolder` is restored and **readable as context** (FR-25) but is **NOT writable by the AI** — exactly as a normally-opened out-of-root tab (FR-26 / A-2). The restore path must not grant the AI write access to a tab that falls outside the sandbox root.

**FS-1 — the single Folder + AI-write root, recomputed every launch (Decision A, FINAL — replaces the MA5 dimension above).** `openFolder`/`canonicalOpenFolder` are no longer read on restore to decide the AI sandbox root; instead HoardPad resolves ONE root every launch, in this exact tier order:
- **Tier (i) — file(s) passed in** (double-click / "Open With"): root = the first passed file's containing folder. The prior session's tabs still restore in their saved order; the passed file(s) open as additional tabs, the first passed file active. A passed file already among the restored tabs is deduped (the existing tab is focused, not duplicated).
- **Tier (ii) — no file passed, restored tabs exist:** root = the folder of the first tab (in restore order) that has a saved on-disk path, skipping scratch/untitled buffers. No path-bearing tab falls through to tier (iii).
- **Tier (iii) — neither:** root = the user's My Documents folder (`Environment.SpecialFolder.MyDocuments`, honoring `XDG_DOCUMENTS_DIR` on Linux; falls back to `~/Documents`, created if missing, when the OS API returns an empty string — the gap BUG-10 found); the folder-tree pane stays **collapsed** until the user summons it, though the AI panel's scope line still shows the derived root so the safety boundary stays legible (DP-2).

AI write agency still does **not** arm at startup under any tier — it arms on the first write-mode AI action (the existing QA2-18 lazy-arm posture); read/chat is available immediately. File ▸ Open Folder still overrides the root for the **current session only** and is never separately persisted.

**`.hoard` baseline comparison is over canonical-parsed content (MA5, couples to MA2) — scope of the no-spurious-conflict guarantee (R3-mi6).** Dimension 3's present-unchanged vs present-changed-externally comparison for a `kind: hoard` tab is over the **canonical-parsed content**, not raw bytes — because a whitespace-only or escaping-only reserialization by another build (MA2) flips a raw-bytes baseline hash and would trigger a **spurious** conflict prompt on every synced `.hoard`. Parsing both sides to canonical form (per §9.1's pinned encoder/ordering) and comparing the canonical serialization avoids the false conflict. **The guarantee holds only insofar as both synced builds produce the same canonical form.** On the default `[JsonExtensionData]` path (§9.1), an older build relocates an interleaved-unknown-key to the tail, so two **mismatched** builds canonicalize a foreign-authored file differently — and the canonical comparison can still flip on the **first** cross-build restore. This is **scoped honestly to match the §9.1 MA2 decision**: canonical comparison removes whitespace/escaping-only false conflicts, but a genuine known/unknown-boundary relocation between mismatched builds is a **one-time accepted conflict on first cross-build restore** (the same accepted one-time canonicalizing diff §9.1 accepts), **unless** tech-design adopts §9.1's optional custom raw-key-order converter (which would eliminate the relocation and make the no-spurious-conflict guarantee absolute). Tech-design's §9.1 converter choice and this §9.2 scope move together. (For `kind: file` tabs, the comparison remains over raw bytes; only `.hoard`, which HoardPad reserializes, uses canonical comparison.)

**Tie-break / authority edge cases (B6; same-machine tie-break + Save-As stale-path rule, R3-MA1 (MA6+MA10); machine-local recovery dir, R4-MA1):**
- **Duplicate `tabId` across two snapshots — same-machine crash-mid-write tie-break (R3-MA1 (MA6+MA10); machine-local per R4-MA1).** Because the recovery directory is **machine-local and not synced (R4-MA1)**, two snapshots for the same `tabId` can only co-exist on the **same machine** — e.g. a crash *between* two snapshot writes leaves two snapshots of one `tabId`. A **monotonic per-machine sequence counter** orders these correctly, since both were written by the same counter: keep the snapshot with the higher `seq` (the more-recently-written same-machine snapshot); the loser is discarded and logged. The earlier "two synced machines seconds apart" wall-clock justification is **dropped** for the *snapshot* tie-break — that cross-machine clock-skew risk lives on the **on-disk-file dimension** (dimension 3's baseline `contentHash` + `mtime` comparison), **not** on recovery snapshots, which never cross machines, so the snapshot tie-break never compares two machines' counters. `savedAt` (wall-clock) remains only a **secondary** tie-break. **`seq`-missing-or-tied case:** if `seq` does not distinguish the two (e.g. a legacy snapshot lacking the counter), fall back to `savedAt`, and if `savedAt` is also missing or equal, **surface a conflict** (keep-A / keep-B / diff, per FR-19) rather than silently guessing — a duplicate `tabId` that cannot be ordered is a genuine ambiguity, not a tie to resolve arbitrarily.
- **Snapshot-embedded `path` vs session `path` disagree for the same `tabId` — Save-As cannot strand a stale snapshot path (R3-MA1 (MA6+MA10)).** The recovery directory is the source of truth for buffer bytes, but **`path` authority follows whichever of {snapshot, session-entry} was persisted more recently** (by the same monotonic per-machine sequence counter above), so a **Save-As** performed after the last snapshot but before a crash — which updates `session.json`'s `path` while the snapshot still holds the old `path` — does **not** cause restore to clobber at the stale location. A stranded stale `path` is inherently a **single-machine event** (the Save-As and the crash happen on one machine; the recovery dir is machine-local), so the per-machine `seq` orders it correctly. Equivalently (and the implementation tech-design picks): **Save-As forces an immediate recovery snapshot**, so the snapshot's embedded `path` is never staler than the session entry. Absent a more-recent session entry, the snapshot's embedded `path` remains authoritative (the snapshot was written atomically with its own metadata, whereas `session.json` is a rebuildable hint that may lag the last snapshot).
- **`kind` changed scratch→file between snapshot and crash:** the **snapshot's `kind` is authoritative** (it reflects the buffer's last persisted reality); if the snapshot says `file` with a `path`, reconcile via dimension 3; if `scratch`, restore as scratch regardless of a stale session entry.

### 9.3 Activity log shape

The AI activity log (FR-29) is an append-mostly newline-delimited JSON (NDJSON) file per session under the app data directory. Each line:

```json
{ "ts": "2026-06-13T18:04:22.117Z", "requestId": "turn-7f3a", "backend": "claude-cli", "configuredMode": "auto-apply", "agencyMode": "approve-each", "downgradeReason": "clobber", "op": "move", "paths": { "target": "/home/you/notes/b.md", "source": "/home/you/notes/a.md", "dest": "/home/you/notes/b.md" }, "outcome": "applied", "bytesBefore": 1840, "bytesAfter": 1912, "undoRef": "undo/turn-7f3a-03", "durationMs": 41, "error": null, "tokens": { "input": 5120, "output": 380 }, "costUsd": 0.012 }
```

Fields: `op` ∈ {`read`,`create`,`copy`,`move`,`edit`,`delete`,`blocked`}; `outcome` ∈ {`applied`,`blocked`,`undone`,`failed`,`queued`} (`queued` = failed-closed and parked in the FR-39 pending-proposals surface); `backend` ∈ {`claude-cli`,`anthropic-api`,`local`}; `requestId` correlates all ops from one AI turn (the document standardizes on `requestId`; there is no `sessionId`, mi6) (a `requestId` spans **one `claude -p` invocation**; the per-turn caps' no-re-arm state has a **distinct, longer lifetime — the user-initiated conversation — persisted by HoardPad across continuation turns per FR-40's *Cap-state lifetime* clause**, so multiple `requestId`s in one conversation share one cap-state, R5-BL1); `bytesBefore`/`bytesAfter` are size deltas only; `undoRef` points at the undo-journal entry (§9.4) (or a marker that undo is unavailable, FR-28(iii)); `error` is a sanitized reason when `outcome: failed`; `durationMs` is op duration; `tokens`/`costUsd` are optional and populated for `claude -p` from the agent's result message. **API keys and file contents are never written to this log** (NFR-7).

**Agency / downgrade fields (MA13 — make FR-10/FR-38 Done-when provable):**
- `configuredMode` ∈ {`auto-apply`,`approve-each`,`read-only`} — the agency mode the user *configured* (FR-27).
- `agencyMode` ∈ {`auto-apply`,`approve-each`,`read-only`} — the **effective** mode that actually gated this op (e.g. `approve-each` when FR-10 downgraded an `auto-apply` op). A natively-`approve-each` op and a downgraded one would otherwise be indistinguishable; `configuredMode` + `downgradeReason` disambiguate them.
- `downgradeReason` ∈ {`none`,`home-root`,`large-root`,`over-cap`,`clobber`,`degraded`,`create-cap`,`destructive-cap`,`files-touched-cap`} — **why** the op was gated/downgraded (or `none` when `agencyMode == configuredMode` with no trigger). **`files-touched-cap`** records a pause at the FR-40 per-turn distinct-files-touched cap (R4-BL2), distinct from `create-cap` (FR-11) and `destructive-cap` (FR-38) so a sign-off fixture can assert which aggregate or per-op cap fired. This is what lets the FR-10 / FR-38 sign-off fixtures assert the safety net engaged for the **right reason**. **`home-root` and `large-root` are split (R3-mi8)** because FR-10(a) describes the home-directory trigger and the over-threshold-writable-set trigger as an explicit `OR` with *different* user-facing announcements; a single collapsed value could not tell a sign-off fixture which of the two fired, so each maps 1:1 to its trigger like every other `downgradeReason` value.

**`paths` shape (MA13):** `paths` is an **object** (not a flat array): `target` always present; `source` + `dest` present for `move`/`copy`; for a clobbering move/copy, `dest` **is** the clobbered destination (so the log records which file was overwritten). This matches the undo-journal `paths` object (§9.4).

**Cap-interaction counting rule (R3-mi3) — one rule, applied to both per-turn caps (FR-11/FR-38):**
- **The caps count *applied* ops, not *attempted* ops.** An op that is denied/blocked (out-of-sandbox, or denied at the cap boundary) does **not** increment the counter; an op that proceeds (silently or after a confirm) does. Counting attempts would let a denied out-of-sandbox probe burn the cap.
- **An op is counted by exactly one *per-op* cap, and separately by the FR-40 aggregate.** A create increments only the FR-11 create cap; a destructive op (per the FR-38 classifier predicate) increments only the FR-38 destructive cap — the two per-op caps are disjoint. **Independently of which per-op cap (if any) it hits, every create and every overwrite-onto-an-existing-file also adds its target to the FR-40 distinct-files-touched set (R4-BL2)** — FR-40 is an orthogonal aggregate axis, not a re-count: a sub-X% overwrite that increments *no* per-op cap still increments FR-40, and a single file touched twice in one turn counts once toward FR-40.
- **An over-cap op individually confirmed via FR-10(b)(i) still increments the FR-38 counter when applied** — the individual undo-unavailable confirm and the per-turn cap are independent gates; the same applied destructive op is subject to both but **counted once** (toward FR-38).
- **A clobbering move/copy is not double-counted** — it is governed by FR-10(b)(ii)'s individual clobber confirm and is **not** additionally counted toward the FR-38 destructive cap (MA11; Archetype-B-only per R3-BL1).
- **Asymmetry — a clobbering full-overwrite gets NO individual confirm (R3-mi3).** A clobbering **full-overwrite** (a whole-file `Write` / full-file `Edit` onto an existing file that is *under* the size cap) is **not** covered by FR-10(b)(ii) (which is move/copy only) — so it receives **no individual clobber confirm** and is governed **only** by the FR-38 destructive cap (and the FR-40 files-touched aggregate). This is a deliberate asymmetry vs a clobbering move (which always confirms individually): an in-place overwrite of an under-cap file is journaled and undoable, so silent-but-recoverable apply is the accepted posture (R3-MA5), whereas a move's clobbered destination warranted the always-on individual capture+confirm. Stated here so a reader does not assume overwrite parity with move.
- **Sub-threshold ops are silent because NOT COUNTED by the FR-38 classifier, not because they are an early counted op (R4-mi5).** An under-cap overwrite is journaled and undoable, so silent-but-recoverable apply is accepted (R3-MA5) — but the precise reason a **sub-X% / partial-edit** op is silent is that the **FR-38 classifier never *counts* it** (partial edits and sub-threshold overwrites are excluded from the predicate), **not** that it happens to be the 1st–9th *counted* destructive op. This distinction matters: an unbounded run of FR-38-uncounted ops would be unbounded on the per-op axis, which is exactly why the aggregate **FR-40 files-touched cap (R4-BL2)** is the backstop — every overwrite increments FR-40 regardless of magnitude, so the sub-threshold band is bounded on the aggregate axis even though no per-op FR-38 count fires. (Cross-ref: FR-40, NFR-10/C-4 honesty band.)

**Append durability for an append-mostly file (MA3 — reconciles with NFR-4; per-record fsync + truncate-repair, R3-MA2; CONFIRMED by SPIKE-5, 2026-06-19).** NFR-4's temp+rename atomic model covers whole-file **create** (line 1 of a fresh log, via the Windows create-when-absent path) but **not** the in-place appends of lines 2..N — a plain `O_APPEND`+`fsync` still has a torn-final-record window on power loss (a multi-block line `write()` is not crash-atomic). Because this log is the **only durable record** of an undo-unavailable over-cap destroy (FR-28(iii)) and of a failed-closed queued op (FR-39), each appended record is written as a **checksummed, length-prefixed record — PINNED byte layout (tech-design §3.3): `[4B uint32 LE length][N B UTF-8 JSON payload][4B uint32 CRC-32/ISO-HDLC of payload]`, 8 B overhead.** **SPIKE-5 implemented and crash-tested this** (torn-tail truncate-repair PASS across all three torn-record shapes; interior-corruption contrast PASS; per-record-append p50 ~0.6–0.7 ms / p90 ~1.1–1.5 ms on local ext4 SSD, ~14–49 ms for a 25-op turn; **`resync-and-continue` is the named non-ordering-FS fallback** (R4-mi4) with the honest B4 ghost-record false-positive characterization ~0.0004%/corrupt record/64 KB carried). Three coupled durability rules make recovery provable (R3-MA2):
- **(a) Per-record `fsync` before the next append begins.** Each appended record is `fsync`'d to disk **before the next record's append starts** — without this the OS can flush buffered appends out of order on power loss, leaving a genuine *interior* hole (an intact record after a missing/torn earlier one), which the recovery rule below does **not** handle. Per-record `fsync` guarantees that the **only** record that can ever be invalid is the **final, in-flight one** — making "torn tail" provably equal to "first invalid record." **Throughput cost (R4-mi3):** a chatty multi-op AI turn pays one `fsync` per appended record, so the per-turn append cost is bounded by **`(ops × fsync-latency)`** — affordable on local SSD (Lane 2 measured ~0.65 ms/`fsync` on the reference hardware, ~50–100 ms for a 25-op turn) but reaching **seconds on a slow / network / synced target**; SPIKE-5(a) measures the per-record-append throughput so the cost on the deployment target is known, not assumed.
- **(b) On open, truncate-repair to the last validated record offset before appending.** A documented **"discard a torn trailing record on read" recovery rule** drops the trailing record whose length/checksum does not validate and recovers all complete prior records — and on open the file is **physically truncated to the last validated record's end offset** before any new append, so torn bytes are not left on disk for the next append to write *after* (which would permanently embed a corrupt mid-file record). Read-time discard alone is insufficient; the truncate-repair is required.
- **(c) The trailing-record-only recovery rule is correct *because* of (a).** The "discard torn tail" rule is sound only because per-record `fsync` (a) guarantees no interior record can be invalid; a reader must **not** "stop at the first record whose length/checksum fails" in a way that silently discards intact later records (a repro confirmed a literal stop-at-first-bad reader, given a corrupt record #2 with intact #3–#5, returned only #1). The interior-hole-impossibility of (a) **leans on the target FS providing `fsync` write-ordering** (a barrier-honoring journaled FS on local SSD) — a named, not silently-absolute, assumption (R4-mi4). If interior corruption is ever in scope — i.e. the target FS does **not** provide `fsync` write-ordering (a lying disk cache, or a network/synced FS that reorders) — the documented escape hatch is **resync-and-continue** (scan past a bad interior record to recover intact later records), **not** stop-at-first-bad; on a write-ordering FS (the v1 local-SSD target), (a) makes this case unreachable.

A fault-injection test kills mid-append and asserts the reader recovers all complete prior records and truncate-repairs the torn tail (MA3); a **second fault-injection case corrupts an interior (non-final) record and asserts the (a)+(b) model prevents an interior hole** (R3-MA2, SPIKE-5(a)/A-6). The same per-record-`fsync` + checksummed/length-prefixed + truncate-repair append model applies to the undo journal (§9.4) when its entries are appended.

**Op-enum relationship to §9.4 (mi5).** The §9.4 undo-journal `op` enum (`create`/`copy`/`move`/`edit`/`delete`) is a **deliberate subset** of this §9.3 enum: it **excludes `read` and `blocked`** because those are never undoable (a read mutates nothing; a blocked op never applied), so they have no before-image and never enter the undo journal.

### 9.4 Undo-journal schema

The undo journal (FR-28's durable backing structure) is a structure **separate from the activity log** (§9.3): the activity log is a human-readable record that carries no file contents, while the undo journal holds the before-images needed to actually reverse an op. It is stored under the app data directory and ordered to permit reverse-order replay. **Op vocabulary (MA11):** the `op` enum is `create`/`copy`/`move`/`edit`/`delete` — there is **no `rename`**; a rename canonicalizes to `move` (FR-26), so a clobbering rename is captured as a clobbering `move` (with `destPriorContent`). **Append durability (MA3; per-record fsync + truncate-repair, R3-MA2):** if journal entries are appended (rather than each written whole-file via temp+rename), they use the same **checksummed/length-prefixed NDJSON record** format, the **per-record `fsync`-before-next-append** rule, the **on-open truncate-repair to the last validated record offset**, and the **"discard a torn trailing record on read"** recovery rule as §9.3 — so the trailing-record-only recovery is provably correct and no interior hole can form; before-image blobs (`before/…bin`) are whole-file create+`fsync` per NFR-4. **Cross-session retention (MA8) — keyed on a durable, path-independent buffer journal id (R3-mi5):** a buffer's journal entries are kept until that buffer is cleanly saved and closed, else pruned after **7 days OR 50 ops per buffer, whichever first** (FR-28). "A buffer" is identified by a **durable `bufferJournalId`** minted when the buffer first acquires an undo entry and **independent of path** — because path-keyed retention orphans on a Save-As or an AI rename (`move`), and `tabId`-keyed retention dies at session end (leaving cross-session retention nothing to anchor to). The `bufferJournalId` is recorded on each journal entry and carried in the recovery snapshot so a scratch/path-less buffer, a Save-As'd buffer, and an AI-renamed `.hoard` all keep one stable retention key across sessions. Per-entry shape:

```json
{
  "undoRef": "undo/turn-7f3a-03",
  "requestId": "turn-7f3a",
  "op": "edit",
  "paths": { "target": "/home/you/notes/todo.md" },
  "priorContent": { "kind": "blob", "ref": "before/turn-7f3a-03.bin" },
  "preOpContentHash": "sha256:9b1c…",
  "preOpMtime": "2026-06-13T18:04:22.061Z",
  "snapshotSkipped": false
}
```

Field contract:

| Path | Type | Notes |
|---|---|---|
| `undoRef` | string | Stable id; **matches** the activity-log `undoRef` (§9.3 join). |
| `bufferJournalId` | string | **Durable, path-independent buffer journal id (R3-mi5)** — the MA8 cross-session retention key. Minted on the buffer's first undo entry; survives Save-As / AI-rename (`move`) / session end; carried in the recovery snapshot so retention anchors to the buffer, not its path or `tabId`. |
| `requestId` | string | The AI turn this op belonged to (reverse-order replay groups by, then orders within, the turn). |
| `op` | enum | `create` / `copy` / `move` / `edit` / `delete`. |
| `paths` | object | `target` always; `source`+`dest` for `move`/`copy`. |
| `priorContent` | object \| null | The before-image: inline bytes or a pointer (`ref`) to a stored before-image blob. **`null` for `create`** (nothing existed before; undo deletes the created file if unchanged). Written + `fsync`'d **before** the destructive op mutates the target (M15). |
| `destPriorContent` | object \| null | **Before-image of the CLOBBERED destination (Decision 1 / M10):** for a `move`/`copy` whose `dest` **already existed**, the destination's prior bytes (blob ref), so undo restores the clobbered file's content — not just the move mapping. `null` when the destination did not pre-exist. A clobbering move/copy only proceeds after the FR-10(b) confirm. |
| `destPriorContentHash` | string \| null | Pre-op content hash of a pre-existing `dest` (drives external-mod detection on the destination, FR-28(ii)); `null` when `dest` did not pre-exist. |
| `preOpContentHash` | string \| null | Hash of the target's content immediately before the op (null for `create`). Drives FR-28(ii) external-modification detection. |
| `preOpMtime` | string \| null | Target mtime immediately before the op (null for `create`). |
| `snapshotSkipped` | boolean | `true` when the file exceeded the snapshot size cap (FR-28(iii)) → **undo unavailable** for that op; the activity-log `undoRef` then carries the undo-unavailable marker. |

**Reversal is pure decision logic in the shared domain (C-9):** given an entry and the **injected current** `contentHash`/`mtime` of the target, the domain decides the reverse action, replaying entries in **reverse activity-log order**. FR-28(ii) "external modification detected" is computed by comparing the journal's stored `preOpContentHash`/`preOpMtime` against the current file **before** applying undo — **the content hash is authoritative for the safety decision; `mtime` is only an optimization to skip a re-hash, never the sole basis** (M14 — coarse mtime resolution can mask a same-tick edit, and a sync daemon touching mtime can cause spurious refusal). To close the **check→restore TOCTOU** (M14), the host **holds a file handle / re-verifies the hash immediately before the restore write**, not only at decision time. **Over-cap ops never attempt restore:** an entry with `snapshotSkipped: true` has no `priorContent`/`preOpContentHash`, so undo for it is reported unavailable and the restore path is never entered (M14). **Write ordering (M15):** for any destructive op, the before-image blob(s) (`priorContent`, and `destPriorContent` for a clobbering move/copy) **and** this journal entry are `fsync`'d to disk **before** the op is permitted to mutate the target; a crash between before-image write and target mutation must still recover the original (FR-28 Done-when crash-injection test). The host supplies the current-file hash/mtime read and the byte I/O; the domain owns the decision. Cross-reference: FR-10, FR-28, §9.3.

## 10. Constraints & assumptions

Assumptions that, if false, change the project materially. Includes the hidden assumptions from `brief.md`, each now resolved to an explicit rule.

- **A-1 (`claude` CLI present, default backend).** The default backend assumes the `claude` CLI is installed and authenticated on the machine and resolvable on PATH (or at a configured path, FR-24). If absent, FR-24's readiness check surfaces an actionable error and the user can switch to another backend; the app does not crash or block startup on a missing CLI.
- **A-2 (open-folder root-resolution rule — RESOLVED; with smart-downgrade on large/home roots, Decision 1).** The AI sandbox root is the **active open folder's resolved absolute path**. When files from multiple different folders are open as tabs, the sandbox root remains the single active open folder, **not** the union of the tabs' parent directories. Open tabs outside the root are readable as context (FR-25) but are **not** writable by the AI (writes are constrained to the root, FR-26). If **no folder is open**, AI file-write agency is disabled (FR-26); the user must open a folder to grant write scope. **A root that is the user's home directory, or whose writable set exceeds the file-count threshold, does not silently grant blanket auto-apply** — per FR-10(a) it auto-downgrades to per-op confirm (the "cannot escape the root" boundary protects little when the root is the user's whole working tree). The file-count trigger counts the **writable set — all sandbox-writable regular-file descendants — not the `.gitignore`-filtered set** (MA9), because the AI can mutate every writable descendant (writes are not `.gitignore`-filtered) and that is the real blast radius the downgrade must reflect. The writable-set count is a **bounded, early-exitable predicate** (resolve symlinks to canonical paths counted once with a cycle guard, do not cross mount boundaries, exclude special files, abort at threshold+1, run off the UI thread — FR-10(a)/R3-MA4), and it is **re-counted at op-time (or on a debounced file-watch)**, not cached from folder-open, so a folder that grows past the threshold mid-session still triggers the downgrade (R3-MA1/MA10). There is one active open folder per window in v1.
- **A-3 (rendered preview is read-only — RESOLVED).** The Markdown rendered preview is read-only; all editing happens in source view (FR-15). WYSIWYG editing is a permanent v1 non-goal (§4.2).
- **A-4 (local-disk files; single-FS atomicity enforced, not just assumed, M16).** Files live on the local filesystem; no cloud/remote file providers in v1. Atomic-write durability requires the **temp file to live in the target's own directory** (same filesystem) so `rename` is atomic; HoardPad enforces this rather than assuming it (NFR-4). On a **network/synced/cross-device target** (`EXDEV`, SMB/NFS, Dropbox/Syncthing), atomic `rename` is unavailable and HoardPad falls back to an `fsync`'d in-place write **with a warning that zero-loss atomicity is not guaranteed there** (NFR-4). Plainly: `.hoard` zero-loss (SC-6a) is guaranteed for **local same-filesystem** targets; on a synced folder it is best-effort with a surfaced warning. (The §9.1 overflow-bag defense addresses cross-*version* key loss on synced files — a separate concern from the crash-atomicity guarantee.)
- **A-5 (single window).** v1 is single-window per process (single-instance behavior is a tech-design detail). Multi-window is not required for any FR.
- **A-6 (fixture-authoring is a sized work item, not an assumption — m4).** SC-3/SC-4/SC-5/SC-6 acceptance depends on a curated fixture set: a per-language token-class fixture for each of the 20 languages (SC-3), a feature-exercising Markdown torture-test doc (SC-4/FR-16/the renderer-fidelity spike), the **crafted `tool_input` payloads driving the real Archetype-A `claude -p` PreToolUse hook subprocess** (create/edit/out-of-sandbox/clobber — SC-5(i) deterministic gate, BL3) **and** the separate **scripted/mock tool-call sequence through the shared file-ops service** for the Archetype-B gate (SC-5(ia)), the **poisoned-README injection fixture** asserting confirms ≥ 1 (FR-10/FR-38/FR-40/NFR-10/B5) — including the **Archetype-A variant that routes the over-cap overwrites through single-hunk full-file `Edit` calls and asserts FR-38 still fires (R3-BL1)**, the **`Edit`-create FR-11-bypass variant** (>cap creates via empty-`old_string` `Edit` on non-existent paths, held at the FR-11 cap and counted by FR-40, R4-BL1), the **sub-threshold-overwrite variant** (≥ N distinct in-root files each sub-X%, held at the FR-40 files-touched cap though FR-38/FR-11 do not fire, R4-BL2), the **FR-40 cross-continuation persistence fixture** (after a >cap trip, a second batch into the **same conversation-keyed counter** still confirms at the (N+1)th cumulative distinct file — no re-arm across the HoardPad-initiated continuation; a new user-initiated conversation starts a fresh set — R5-BL1, deterministic, no live LLM) **and the substitution-after-pause assertion** that `AskUserQuestion`/`ToolSearch` are denied after an FR-40 pause (R5-mi3), and the separate **Archetype-B delete-based variant** through the shared file-ops service, the **rename-onto-open-dirty-tab fixture** (MA11), the **in-bounds symlink-target overwrite fixture** (mi4), the **truncate-to-0 pre-op-size fixture** (mi3), the **append-log torn-tail, interior-bad-record (R3-MA2), and Windows-first-create crash fixtures** (MA3/MA4), the **mid-turn hook-stall fixture** (MA14), and a reorderable/checkable `.hoard` covering drag-while-checked under all three modes incl. partition edges (SC-6b/FR-33/mi9).
